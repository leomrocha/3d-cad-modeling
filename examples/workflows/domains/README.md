# Domain workflow reference examples

These eight routes show how source evidence becomes editable CAD, semantic IFC, robot descriptions, collision geometry, and display scenes. They are proposed adapter workflows, not completed integrations. The machine-readable contracts and source register are [domain-details.json](/home/leo/projects/3dmodeling/research/workflows/details/domain-details.json) and [domain-detail-sources.json](/home/leo/projects/3dmodeling/research/sources/round-03/domain-detail-sources.json). Workflow IDs retain their identifiers from the workflow map.

## Effort and compute comparisons

Ratings in the JSON use the scales in [contract.json](/home/leo/projects/3dmodeling/research/workflows/details/contract.json). Human effort, setup effort, and compute are separate ordinal assessments. They assume the clean inputs named in each workflow and are not elapsed-time or hardware benchmarks.

With those conditions, approximate human effort from lowest to highest is: **DOM-R05** sketch over a measured native model; **DOM-R07** identified library object placement; **DOM-R08** registered scan to static collision; **DOM-R02** supplier STEP to robot link; **DOM-R03** CAD assembly to URDF/MJCF; **DOM-R06** photo set to measured component; **DOM-R01** plan plus survey to registered IFC; **DOM-R04** robot, Menagerie assets and registered environment composition. A clean vector plan with authored dimensions makes the IFC-only branch of DOM-R01 much easier than raster interpretation plus scan registration.

Compute demand is lowest for DOM-R05, DOM-R02, DOM-R03 and DOM-R07: mostly transforms, CAD-kernel operations, and small XML/IFC graphs. DOM-R08 and the collision preparation in DOM-R04 scale with cloud and mesh size. DOM-R01 and DOM-R06 become heavier when they include dense multi-view stereo, depth maps and large point clouds. The optional TripoSR single-image route is appearance reconstruction; its model card/source reports a default route around 6 GB VRAM and a slower CPU fallback. That route does not produce metric interfaces. The COLMAP dense route can use CUDA; source images, camera count, depth maps, cloud size and mesh triangles drive memory and storage. No workflow runtime was measured.

## Reference code

[ifc_model.py](/home/leo/projects/3dmodeling/examples/workflows/domains/ifc_model.py) accepts JSON with explicit metre values, project/site/building/storey names, wall endpoints, thickness/heights, rectangular opening measurements and optional complete CRS/map-conversion data. Run it as `python examples/workflows/domains/ifc_model.py input.json new-model.ifc`. It uses IfcOpenShell API calls to make an IFC4 hierarchy, units, straight walls and void features. It does not vectorize a plan, infer elements, author rooms/materials/door fillings, or validate the result. Opening elements attach through `IfcRelVoidsElement`; the sample does not spatially contain openings.

[robot_model.py](/home/leo/projects/3dmodeling/examples/workflows/domains/robot_model.py) accepts explicit SI-unit MJCF body/joint/inertial records and external mesh paths with per-asset source URL, license, license URL and expected SHA-256. Run it as `python examples/workflows/domains/robot_model.py input.json new-model.xml`; it creates a sibling `.manifest.json` and refuses to overwrite either file. `fullinertia` is expressed in body axes; MJCF does not permit combining that attribute with an inertial-frame quaternion. The writer checks explicit source fields and positive-definite inertia, serializes a bounded body tree, and checks XML syntax. It does not infer kinematics, calculate physical properties, create actuators, convert CAD, model closed chains, compile with MuJoCo, or establish physical validity. Asset paths are absolute in the MJCF; moving a package requires a reviewed path rewrite.

The robot JSON has these required records: `units` must declare length `m`, angle `rad`, mass `kg`, and inertia `kg*m^2`; `model` supplies a name and `physics.timestep_s` plus `physics.gravity_m_s2`; `meshes[]` supplies unique `id`, file, positive `scale`, role, source URL, license, license URL and SHA-256; `bodies[]` supplies a body `name`, `pos_m`, unit `quat_wxyz`, joint record, inertial record, geometry list and optional nested `children`. Each joint supplies a type (`fixed`, `hinge`, `slide`, or root-only `free`) and source/evidence status; movable joints also supply name, `pos_m`, unit `axis` and increasing `range`. Each inertial record supplies `mass_kg`, `pos_m`, `frame: "body"`, `fullinertia_kg_m2` in MJCF order `ixx iyy izz ixy ixz iyz`, mass/inertia sources and evidence status. Each geometry record supplies a mesh ID, role, `pos_m` and unit `quat_wxyz`. Names must be unique and every referenced mesh ID must exist. No sample numbers are prescribed; values come from project evidence.

Both scripts are reference code. Their required APIs and dependencies are recorded in the dossier. They were not integration-run here. `ifc_model.py` requires Python, NumPy, and an IfcOpenShell build exposing the documented API calls. `robot_model.py` uses Python standard-library modules; MuJoCo is needed for the independent `mujoco.MjModel.from_xml_path(...)` compile check after integration.

## Frame and asset rules

Every placement uses named source and target frames. Building geometry uses declared project axes and storey elevations; map CRS and transform values come from survey evidence. Robot body, joint origin/axis, mesh-local origin, COM and inertia frames remain separate records. Camera and depth sensor extrinsics map sensor frames into the scan/project frame. A 4×4 registration transform must retain direction, units and control-point source. Never derive mass, inertia, joint axes, georeference or mechanical interfaces from visual resemblance alone.

Keep visual and collision geometry as separate files or explicit geom roles. Tessellation, point-cloud filtering, Poisson reconstruction, convex decomposition, and GLB conversion create derivatives with different information. Keep the original CAD/IFC/scan and record derivative hash, method, tool version, parameters, source frame, units and rights. CoACD/V-HACD or primitives are collision approximations; inspect narrow openings and clearances against the visual/engineering source. IFC-to-mesh and BIM-to-MuJoCo paths preserve placement only when mapped explicitly; they do not carry the complete IFC semantic graph into the target.

The Menagerie example uses **Franka Emika Panda** only as an identified reference asset: its model README states MuJoCo 2.3.3 or later and Apache-2.0 for that model. Menagerie terms are per model, and this example does not select a robot for a project. Library software licenses do not grant rights to imported manufacturer, scan, or component files. Store source URL, exact revision or file hash, title/attribution, per-file license/terms, retrieval date, units and local coordinate frame with every reusable asset. Use the rights that apply to the specific file, including supplier terms where no open license is provided.
