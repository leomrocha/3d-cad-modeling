# Contribute a translator improvement

1. Keep the adaptation receipt with the job. Record its readable operation, source procedure and baseline revision, target adapter namespace, changed files and SHA-256 hashes, tests, evidence level and intended repository destinations. A text-only mapping can carry offline evidence.
2. Name the improvement and ask whether the user wants a local contribution preview. Decline or silence ends contribution work. A later request resumes from the same receipt.
3. On opt-in, verify the recorded hashes. Compare the original installed source, job-local improvement and current repository files. Present exact changes and any shareable fixtures. Exclude private paths, credentials, endpoint identifiers, models and job logs. Apply the user's narrowing. Skip an already-present change.
4. In a separate local checkout, create a branch for that improvement. Follow its checkpoint, catalogue, attribution, package finalization and verification rules. Put translator-only code in its canonical namespace. Include the regenerated fourth package and check that existing endpoint packages and their behavior are preserved.
5. Show the final diff, exact commit, checks, publication source/destination and target branch. Ask whether to push this revision and open the pull request. Decline or silence leaves the branch local. Changing the diff or destination requires a new approval. After explicit approval record the successful push and PR separately, including a partial failure and the final PR URL where available.

For an agent implementing these steps, contribution_step in the [planner module](../scripts/translator.py) takes the user's preview choice, the current final scope and the scope the user explicitly approved. A scope contains commit, diff_sha256, destination, source_branch and target_branch. Pass approved_scope only after explicit publication consent. The helper returns the next step without performing Git operations. A publication decline ends the workflow locally.
