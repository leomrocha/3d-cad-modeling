## Representation contracts

A workflow operation consumes the listed required input types and produces only the listed outputs. `input_alternatives` lists OR-groups; every type in one selected group is required. Recipe inputs below are source seeds, not generated intermediates. The graph was checked for availability from those seeds. A passing type chain checks declared data contracts only; it does not mean the workflow was run or physically validated.

Use the editable project-native file as source authority. Keep each conversion output, transformation, mapping, source hash, software/version and units/frame in a manifest. A CAD solid/B-rep, a triangle mesh, an IFC model, a robot description and a rendered scene are different representations with distinct preserved fields. A generated mesh does not carry CAD feature history or building semantics. A model import/export may also change topology, placements, axes, visual detail, or collision surfaces; validate the actual exporter/consumer pair.

## Combined routes and representation boundaries

### Plans, photographs, depth capture and semantic IFC

A raster plan and written brief can seed IFC using IfcOpenShell geometry creation and the project’s building semantic/classification decisions. A photo set can produce camera poses and reconstruction point samples; depth frames can produce a registered point cloud when sensor scale/calibration are retained. Register scans to the IFC frame through measured controls. Keep registration control points and independent checks separate. The IFC remains the semantic model; IfcOpenShell can extract either triangle meshes or OpenCASCADE B-reps, and those choices produce distinct geometry derivatives. A Blender GLB scene is an inspection/render asset, not a replacement for IFC object/property relationships. The local energy-sim IFC provenance example records an actual IFC-to-GLB transform and unit handling; its evidence remains local-source inspection.

Sources: [IfcOpenShell geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html), [geometry API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/geom/index.html), [geometry creation](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_creation.html), [profile representation](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/geometry/add_profile_representation/index.html).

### CAD assemblies and robot simulation

A CAD assembly tree names parts and placements. Articulated behavior needs a separate joint set: parent and child, joint type, frame origin, axis, limits and units. FreeCAD Assembly Workbench documents fixed, revolute, cylindrical, slider, ball, rack-and-pinion, screw, gears and belt joints; an exporter still needs to map those relations into a robot format. The explicit assembly/joint authoring operations in this graph prevent software from silently deriving kinematics from shapes. URDF carries a tree of links and joints and separate visual/collision/inertial elements. MuJoCo loads URDF as a subset; simulator-specific actuators, sensors, contacts and other MJCF properties require MJCF editing. Closed kinematic loops need an explicitly selected representation and constraint treatment; a simple URDF tree cannot preserve a loop as a loop.

For every robot link, keep visual geometry, collision geometry and mass properties separate. MuJoCo uses consistent user-selected units (MKS is recommended), local body/inertial frames and principal inertias; its mesh collision uses convex hulls. OBJ and binary STL are documented mesh inputs. CoACD and V-HACD can produce convex pieces; preserve source mesh, input hash, algorithm/version/settings and frame, then inspect holes and contacts. A collision hull/decomposition is an approximation and is not the visual or manufacturing geometry. Store mass, COM and inertia in explicit frames and units, with source status: measured, vendor claim, calculated or assumed.

Sources: [FreeCAD Assembly Workbench](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Assembly_Workbench.md), [URDF tutorial](https://github.com/ros/urdf_tutorial), [MuJoCo modeling guide](https://github.com/google-deepmind/mujoco/blob/main/doc/modeling.rst), [MuJoCo overview](https://github.com/google-deepmind/mujoco/blob/main/doc/overview.rst), [CoACD licence](https://raw.githubusercontent.com/SarahWeiii/CoACD/main/LICENSE), [V-HACD licence](https://github.com/kmammou/v-hacd/blob/master/LICENSE).

### CAD + Menagerie robot + scanned environment

DOM-R04 starts from an identified real MJCF asset from MuJoCo Menagerie, CAD assembly, explicit joints and photo/depth environment inputs. The path derives robot meshes from the CAD representation and registers capture-derived environment points/mesh. A reviewed mapping operation associates CAD parts with named MJCF bodies while retaining the selected model’s joint topology. The environment mesh then enters as a separate MJCF geom/collision set. Menagerie includes model-specific files and per-model license information; carry its precise asset identity and licence into the component record. CAD is a geometry replacement input, not evidence that the Menagerie model’s dimensions or dynamic parameters match the physical product.

Sources: [MuJoCo Menagerie](https://github.com/google-deepmind/mujoco_menagerie), [Menagerie README](https://github.com/google-deepmind/mujoco_menagerie/blob/main/README.md), [MuJoCo model format](https://github.com/google-deepmind/mujoco/blob/main/doc/modeling.rst).

### Reusable component intake and asset libraries

A source-library intake record must bind the actual asset bytes and revision to original URL, retrieval time, SHA-256, format, units, coordinate frame, part identity, material/mass evidence, attribution, redistribution/modification rights and licence text. Keep each asset’s rights separate from the software/tool licence and the project’s licence. A webpage that offers downloads is not itself proof of open licensing, and “free download” does not establish redistribution permission. Pin revisions in assemblies. A new supplier file, geometry, hash or licence creates a new immutable revision; downstream exports list source revisions and conversion tools.

Actual library/asset sources represented in the graph: [FreeCAD Library](https://github.com/FreeCAD/FreeCAD-library), [FreeCAD Addons](https://www.freecad.org/addons.php?lang=eng_EN), [FreeCAD BIM Library documentation](https://reqrefusion.github.io/FreeCAD-Documentation-html/wiki/BIM_Library.html), [KiCad library licence](https://www.kicad.org/libraries/license/), [Poly Haven asset licence](https://polyhaven.com/license), [MuJoCo Menagerie](https://github.com/google-deepmind/mujoco_menagerie), and [CONTEC download terms](https://www.contec.com/en/download/contract/contract3/?downloaditemid=b1063f2d-146f-4ca4-b8d2-b54c4388c265&itemid=f9a4d3e0-9ca3-4466-9b3d-cffac9355280). These have different asset and redistribution rules; consult the per-item licence/terms before importing content into a redistributed library.

### CAD, STEP and fabrication

The graph distinguishes STEP exchange files from imported CAD solids and assemblies. Export solid and assembly trees on separate adapter paths and record schema/units. Reopen exports with an independent consumer; compare body count, bounds, volume, interfaces and analytic surface types. The local OpenCADStudio STEP writer inspected in earlier baseline work constructs plane faces from triangles, so that path yields faceted surfaces. Do not represent its output as native parametric history or exact curved B-rep. Fabrication output remains a package of native CAD, drawings, material/process notes and neutral exports with revision links; each drawing/export needs dimensional readback.

### Blender orchestration and interactive workflows

Blender can assemble display scenes, inspect multiple source representations and produce image/GLB outputs. Its official scripting API supports automation; MCP adds a live interaction path. The official Blender Foundation-hosted MCP source declares a minimum Blender version that is newer than the local Blender 5.0.1 noted in prior baseline research; keep OCS as the current engineering CAD baseline and treat Blender scripting/bridge compatibility as a later integration check. The community `ahujasid/mcp-for-blender` is a separate implementation and licence/compatibility evidence must not be conflated with the official repository. The assigned UX Planet article’s visible intro describes Claude Code → Blender MCP → Blender; the page was partially accessible and its member-only procedure/code was not inspected.

Sources: [Blender pipeline formats](https://www.blender.org/features/pipeline/), [Blender Foundation MCP repository](https://projects.blender.org/lab/blender_mcp/src/branch/main), [community MCP repository](https://github.com/ahujasid/mcp-for-blender), [Blender scripting notes](https://github.com/blender/blender/blob/main/doc/python_api/rst/info_tips_and_tricks.rst), [assigned UX Planet article](https://uxplanet.org/3d-modeling-with-claude-code-a-practical-blender-workflow-97e6e0b536b0). The article is represented by existing report evidence: visible introduction only; full member-only article inaccessible.

## Frame, asset and licence requirements


Every placement uses named source and target frames. Building geometry uses declared project axes and storey elevations; map CRS and transform values come from survey evidence. Robot body, joint origin/axis, mesh-local origin, COM and inertia frames remain separate records. Camera and depth sensor extrinsics map sensor frames into the scan/project frame. A 4×4 registration transform must retain direction, units and control-point source. Never derive mass, inertia, joint axes, georeference or mechanical interfaces from visual resemblance alone.

Keep visual and collision geometry as separate files or explicit geom roles. Tessellation, point-cloud filtering, Poisson reconstruction, convex decomposition, and GLB conversion create derivatives with different information. Keep the original CAD/IFC/scan and record derivative hash, method, tool version, parameters, source frame, units and rights. CoACD/V-HACD or primitives are collision approximations; inspect narrow openings and clearances against the visual/engineering source. IFC-to-mesh and BIM-to-MuJoCo paths preserve placement only when mapped explicitly; they do not carry the complete IFC semantic graph into the target.

The Menagerie example uses **Franka Emika Panda** only as an identified reference asset: its model README states MuJoCo 2.3.3 or later and Apache-2.0 for that model. Menagerie terms are per model, and this example does not select a robot for a project. Library software licenses do not grant rights to imported manufacturer, scan, or component files. Store source URL, exact revision or file hash, title/attribution, per-file license/terms, retrieval date, units and local coordinate frame with every reusable asset. Use the rights that apply to the specific file, including supplier terms where no open license is provided.
