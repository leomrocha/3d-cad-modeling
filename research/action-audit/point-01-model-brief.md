# Point 01 — Descriptions and explicit dimensions to a model brief

Current execution package: [OCS engineering (`cad-ocs-engineering`)](../../skills/cad-ocs-engineering/SKILL.md). External OCS skill locators below identify the original inspected sources.

Date: 12 November 2026. Procedure status: proposal. Evidence: local source inspection and requirements synthesis. Recorded operations: **CAD-01 — Extract a model brief from text and dimensions** and **DOM-01 — Normalize model brief**.

## 1. Purpose and result

1. **Purpose:** turn supplied descriptions, dimensions and measurement records into a source-linked description of the intended model. Name the components and features, their geometric relationships, units, coordinate frames, controlling dimensions, tolerance requirements and requested outputs.
2. **Result:** one readable model brief, its source index, feature/value records, retained interpretation alternatives, decision questions, branch comparison, merge record and validation findings. These may be sections of one Markdown document. They specify the content to preserve; the storage and runtime implementation remain development proposals.
3. **Engineering goal:** give each subsequent geometry action a precise input: the named feature to construct, the applicable value or relationship, its source and status, its unit/frame, and the check that will evaluate the result.
4. **Generic scope:** apply the procedure to the components and geometry actually described by the supplied evidence. Source-defined units, frames and features determine the brief. This procedure supplies no example part dimensions, plate origin, axis orientation or numerical tolerance.
5. **Relationship to the existing plan:** this point expands the intake action in the [implementation plan](../implementation-plan.md), section 4, and the proposed `model-brief` skill in section 5. The implementation plan retains its current content and status.

## 2. Terms used in the procedure

1. **Model brief:** the source-linked record of geometry intent consumed by a later modeling action. The repository's [representation register](../workflows/representations.json) defines its content as parts, dimensions, units, datums, evidence, interpretation and intended outputs.
2. **Feature:** a named geometric element or relation within a component, such as a surface, opening, axis, interface or placement relation. The supplied task determines the applicable feature kinds.
3. **Coordinate frame:** a named origin, axis directions and handedness used to express positions and orientations. A **datum** is the named reference point, axis or surface from which a dimension or placement is defined.
4. **Tolerance requirement:** the allowed departure from a stated geometry requirement. A dimension can use symmetric limits, unequal limits, a minimum, a maximum or another explicitly sourced acceptance rule.
5. **Measurement uncertainty:** the stated uncertainty of the evidence used for a value. **Numerical comparison tolerance** is the allowed error of a later numerical check. A solver's stopping criterion and an export/readback comparison threshold each have their own role and source. Record these separately from the geometry's tolerance requirement.
6. **Reasoning agent:** a model interpreting source meaning, resolving references and explaining candidate mappings. **VLM** means **vision-language model**: a model that reads images and language together. Its role here is to relate supplied visual marks, labels and features to candidate brief records.
7. **Deterministic software:** a procedure with fixed rules whose result follows from the same inputs and configuration. **Candidate branch:** an isolated proposed interpretation or extraction of the same source revision. **Merge:** the explicit selection and combination of candidate records into one brief.

## 4. Inputs and required output content

1. **Description input:** original wording, source path or original URL, document/page/line or message location, observation date, revision identity and scope of the current request. Preserve explicit corrections and rejected interpretations with their original wording.
2. **Dimension input:** original value text, unit, readable component and feature name, geometric association, source location and evidence status. Keep dimension annotations and their feature associations together.
3. **Measurement input:** measurement value, unit, measured feature or observation points, coordinate frame, measurement method, source identity and supplied uncertainty or accuracy conditions. A measurement-set enters the DOM-01 branch in place of the dimension input.
4. **Optional visual evidence:** supplied image/page and its identity, view identity and page/image location of each supporting mark. Link the original image; cite both a dimension-label region and its associated feature or extension-line endpoints. Keep the full view beside any source crop. Record pixel origin, axis directions and any crop/scale/rotation/deskew mapping back to the original image. PDF evidence retains page index, displayed page label and any page-to-raster transform. These requirements follow the [visual review](reviews/visual-review.md). Source preparation occurs within its authorized scope. This point begins with descriptions and explicit values; drawing reconstruction is a separate operation.
5. **Brief content:** scope and intended downstream artifact; component/feature names; source excerpts and pointers; original and normalized values; units and frames; geometric relationships; per-feature tolerances; evidence status; unresolved decision questions with affected actions; evaluated alternatives; selected candidate records; validation results; resume position.
6. **Input coverage:** CAD-01's current alternatives permit descriptions alone, dimensions alone, or both. DOM-01 requires descriptions and either dimensions or a measurement set. Preserve the intake condition in the brief. A description-only intake can produce feature intent and targeted questions; metric geometry actions consume the feature records that contain their required sourced values.
7. **Output representation:** a requirements document with linked evidence. Later operations create constrained sketches, CAD solids, native model documents or domain-specific geometry using their own inputs and checks.

## 6. Numbered action procedure

### Action 01 — Preserve the input revision and state the job boundary

1. **Goal and inputs:** read the current request, supplied descriptions and explicit values; identify the requested model and the exact next output.
2. **Software work:** retain original files unchanged; record existing local paths or exact supplied URLs, source identity, date and content hash for retained files. Preserve prior revisions and the correction sequence. For a supplied URL, record the actual retrieval/inspection state beside it.
3. **Reasoning work:** identify the supplied scope, intended use, source authority and dependencies. Separate instructions, observations, assumptions and candidate ideas using the wording and provenance of each item.
4. **User decision:** ask an open question when a scope or source-priority ambiguity affects the next action. Name the conflicting statements and the affected feature.
5. **Output and check:** source index plus a scope statement; every retained source has an identity and every explicit correction points to the statement it changes. The original can be reopened from its recorded location.
6. **Resume condition:** retain the source index and the last completed action. A changed source creates a new intake revision; subsequent records refer to that revision.
7. **Basis:** [project instructions](../../AGENTS.md), research registration rules 1–7; OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`), modeling contract steps 1–2.

### Action 02 — Select the execution mode and define candidate branches

1. **Goal and inputs:** use the preserved source set to identify which records are explicit and which require interpretation.
2. **Software work:** identify actual source formats, available machine-readable values and stable identifiers. Record the supported adapter/version for a software-first branch when exercised capability exists.
3. **Reasoning work:** choose a proposed execution mode from section 5 and explain the choice by the source's concrete properties. For difficult inputs, define independent candidate branches: a source-literal interpretation, an independent feature/relationship interpretation and a software extraction branch wherever the source format supports it. Name each branch's intended use, required feature coverage/detail and per-feature accuracy criteria from the task. A branch may cover controlling dimensions while another adds sourced feature relationships; record the target difference and the source subset each uses.
4. **Parallel work:** when authorized, give each branch the same frozen source corpus revision and a separate output location. Record each branch's selected evidence subset; shared controlling evidence uses identical revisions. Each branch records its own candidate values, interpretations, source pointers, model/software identity, local resource observations, remote inference usage, manual interventions and failures. Candidate branches write their own records; the coordinator writes the merged brief.
5. **User decision:** supply any required scope decision before the affected branch runs. Parallel execution follows the current task's authorization.
6. **Output and check:** a branch plan naming the source corpus revision, branch source subset, assigned actions, intended use, required coverage/detail, feature accuracy criteria, component rationale, output ownership, resource-record requirements and evaluation conditions. Verify that every branch receives the same controlling source revisions and that its proposed detail/accuracy target follows the requested use.
7. **Resume condition:** a failed branch can resume from its own last complete action. Retain the surviving candidates and the failed branch's partial result for comparison.
8. **Basis:** [implementation plan](../implementation-plan.md), source intake and proposed skills; [project instructions](../../AGENTS.md), bounded parallel contribution and evidence separation. Branch composition is a proposal.

### Action 03 — Extract source claims and associate each value with its subject

1. **Goal and inputs:** read each supplied statement and value in the preserved sources.
2. **Software work:** copy machine-readable text and tabular cells with their locations and original formatting. Preserve the original numeric token, signs, decimal separator, unit label, inequality and tolerance notation. For JSON, detect duplicate object names through `object_pairs_hook` before creating a dictionary; reject `NaN`, `Infinity` and `-Infinity` through `parse_constant` and check parsed numerical finiteness. Preserve numeric token strings using the appropriate parsing callbacks. For CSV, record encoding/dialect and retain field strings through extraction. A parser reports rejected or ambiguous tokens as exceptions. These behaviors follow the official-library findings in the [source lookup](reviews/source-check.md).
3. **Reasoning work:** name the component, feature and property to which each claim refers. Link a pronoun, repeated name or shorthand only when the cited context supports that association. For visual annotations, a VLM cites the source image/page and relevant region and distinguishes the label from the feature it labels.
4. **User decision:** resolve competing feature associations when the supplied sources support more than one interpretation. Each question includes the source statements and the affected feature names.
5. **Output and check:** a claim record for every relevant statement or value: source location, original text, subject, proposed meaning, evidence status and branch identity. Compare the extracted claims against the original source; count and name omitted or duplicated source items.
6. **Resume condition:** retain an ambiguous token and its source location. Resume its dependent records when the user supplies a clarification or a readable source; continue independent records within the authorized scope.
7. **Basis:** [CAD-01](../workflows/cad-paths.json), preservation/check requirements; [DOM-01](../workflows/domain-paths.json), original wording and evidence status; OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`), source-view inspection; original [JSON](https://docs.python.org/3/library/json.html) and [CSV](https://docs.python.org/3/library/csv.html) documentation inspected by the source-lookup role.

### Action 04 — Identify components, features and geometric relationships

1. **Goal and inputs:** organize the source claims into the component and feature structure needed by the intended model.
2. **Software work:** check name uniqueness, reference resolution and repeated identifiers. Preserve original names beside normalized readable names. Report two claims using one name for different subjects.
3. **Reasoning work:** identify separate components, occurrences, feature boundaries, contact/clearance relationships and any described relative motion. Record the source for each relationship. Keep an interpretation alternative as a named candidate with its consequence for later geometry.
4. **User decision:** select a relationship or component interpretation when that choice is a design decision. Preserve the user's evaluation literally; acceptance uses the exact `MARK AS ACCEPTED` instruction.
5. **Output and check:** a component/feature list and a relationship list, each with source pointers and dependencies. Check that a component named in a dimension exists and that a relation points to the intended features on both sides.
6. **Resume condition:** a changed component identity invalidates its dependent feature associations; retain prior records and rebuild those associations from the changed source revision.
7. **Basis:** OCS model contract (`${CODEX_HOME}/skills/ocs-engineering/references/model-contract.md`), named separate parts, connections/motion and measurable invariants; [CAD-01](../workflows/cad-paths.json), component boundaries and geometry intent.

### Action 05 — Normalize explicit quantities, units, datums and frames

1. **Goal and inputs:** convert source-linked claims into quantities a later model can consume without changing their meaning.
2. **Software work:** parse explicit numbers and units; check quantity type; retain source values beside normalized values and the conversion rule. Construct decimal values from their retained source strings; record arithmetic precision/rounding and preserve the original precision. Use a unit mapping that has a documented source and checked conversions. Apply domain constraints to the named quantity: signed offsets retain their signs. Record source/target frames and an explicitly supplied transform where a coordinate conversion is required.
3. **Reasoning work:** determine which datum and frame a source actually names; associate each dimension with its endpoints, axis, surface or reference plane. Keep size, position and orientation as distinct properties. Trace source-relative terms such as “above” to the source's stated frame.
4. **User decision:** supply a required unit, datum, axis meaning or source-priority decision when the next geometry action depends on it. Offer the cited interpretations and their geometric consequences as proposals.
5. **Output and check:** per-feature quantity records with original/normalized values, units, source location, datum, frame and value status. Recompute each permitted unit conversion; verify that source/target quantity types match and that each positional value names its reference.
6. **Resume condition:** a frame or unit clarification resumes every affected feature from the original source value. Retain the earlier interpretation for traceability.
7. **Basis:** [DOM-01](../workflows/domain-paths.json), unit normalization and preserved source frames; OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`), units/origin/axes/datums; [implementation plan](../implementation-plan.md), interchange and reproducibility checks.

### Action 06 — Record per-feature tolerance and evidence requirements

1. **Goal and inputs:** connect each geometry check to the acceptance rule and evidence that apply to that feature.
2. **Software work:** preserve the exact tolerance notation and its unit. Associate a general source tolerance with only the features covered by that source's applicability conditions. Check that lower/upper bounds and minimum/maximum conditions remain attached to the same feature after conversion.
3. **Reasoning work:** distinguish the nominal geometry requirement, allowed geometric departure, source measurement uncertainty and numerical comparison rule. Keep a later solver stopping criterion and export/readback comparison threshold as separately sourced requirements when those operations apply. Name the intended measurement or geometric relation and its operating/measurement conditions. A categorical relationship such as separate components receives an exact identity/relationship check; a dimensional relationship receives its sourced quantitative rule.
4. **User decision:** supply the allowed error or applicability decision when a later geometry check requires it. An agent can propose a tolerance with its engineering reason and evidence; the proposal keeps that status until the explicit decision is recorded.
5. **Output and check:** for every controlling feature, record component/feature name, quantity or relation, nominal value if applicable, units/frame, tolerance form/value, tolerance source and scope, evidence uncertainty, intended check and responsible decision record. Verify each tolerance against the cited requirement. Preserve features whose pending question blocks a particular numerical check, with the exact question and affected downstream action.
6. **Later OCS handoff:** the existing checker (`${CODEX_HOME}/skills/ocs-engineering/scripts/check_contract.py`) accepts one length/angular tolerance pair per input. A future adapter can group checks only when their required tolerance pair and units agree, while preserving feature identity and source links. Per-feature bounds or tolerance forms outside that supported subset require a suitable checked implementation.
7. **Resume condition:** a changed tolerance source invalidates checks of its covered features. Resume from the recorded source and recalculate only the affected normalized values/check rules.
8. **Basis:** OCS model contract (`${CODEX_HOME}/skills/ocs-engineering/references/model-contract.md`), selected dimensions/tolerances and check interface; [implementation plan](../implementation-plan.md), component geometry and verification specification; [project instructions](../../AGENTS.md), sourced engineering values.

### Action 07 — Evaluate candidate briefs against their source evidence

1. **Goal and inputs:** compare the isolated candidate records against the frozen source revision and requested output.
2. **Software work:** align records by source item and feature identity; compare explicit values, signs, units, datum references, tolerance bounds, required relationships and source coverage. Evaluate each branch against its declared use, coverage/detail and per-feature accuracy criteria, then compare common required records across branches. Produce record-level disagreements and exception causes. Classify each difference as transcription, unit conversion, frame conversion, feature association, relationship interpretation, source conflict or added detail.
3. **Reasoning work:** evaluate each candidate's interpretation using its cited source. For visual evidence, give a VLM the original full view/page, label region, associated endpoints/features, relevant text and competing records. Require an evidence-based assessment for each disputed feature or label association. For text-only evidence, use a reasoning review of source passages and competing meanings. Select the supported interpretation when the sources and existing task requirements determine it; record the concrete reason.
4. **Evaluation result:** use concrete findings such as “source states this value,” “source associates this label with this feature,” “candidate omits this relationship,” or “these two source passages conflict.” A VLM confidence score may accompany its finding; the source evidence and the deterministic value checks determine the record's support.
5. **User decision:** resolve a source conflict or design interpretation when evidence permits multiple outcomes. Multiple agents agreeing on an interpretation supplies a comparison result; the disputed source still determines what question needs an answer.
6. **Output and check:** an evidence assessment for each differing record, the source region/passage, numerical checks, branch identity, evaluator identity and proposed selection. Verify that every selected claim points to an input source or a separately recorded user decision.
7. **Resume condition:** insufficient visual legibility produces a request for the exact affected label/association or a clearer supplied source. A failed evaluator leaves candidate records intact and can resume from the frozen comparison set.
8. **Basis:** OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`), source inspection and distinction between visual inspection and measured checks; [CAD-01](../workflows/cad-paths.json), source/value preservation. Candidate evaluation by a VLM is a proposed composition of these requirements.

### Action 08 — Select supported records and merge compatible contributions

1. **Goal and inputs:** produce one coherent brief from evaluated candidates and recorded user decisions.
2. **Software work:** carry selected records and their source links into the merged document; record the originating branch and comparison finding. Detect duplicate identities, conflicting values and dangling feature/frame references.
3. **Reasoning work:** select a whole candidate when its evidence and completeness support the requested brief, or merge complementary records from several candidates. The reasoning agent or VLM can perform this evidence-supported selection within the task's existing requirements. Before merging, check common source revision, component identity, units, frames, datum meaning, tolerance applicability and interpretation dependencies. Record the reason for every disputed selection.
4. **Conflict rule:** preserve conflicting candidate values and meanings as alternatives and name the dependent actions. A merge combines compatible sourced records. Competing values require a source-priority decision or corrected evidence; averaging would create a new calculated proposal with its own method and authorization.
5. **User decision:** record explicit choices and exact evaluations. Keep proposal status for the new procedure and its alternatives; a selection for one brief applies to that brief's stated scope.
6. **Output and check:** merged brief plus a selection record containing retained candidate contributions, discarded candidate interpretations with reasons, preserved conflicts and sources. Recheck every cross-feature relationship affected by the merge.
7. **Resume condition:** a branch revision replaces only the records that depend on it. Reopen the associated evaluations and then execute post-merge validation again.
8. **Basis:** [CAD-01](../workflows/cad-paths.json), source associations and unresolved choices; [DOM-01](../workflows/domain-paths.json), preserved units/frames/status; [project instructions](../../AGENTS.md), proposal and decision separation. Record selection/merge is a proposal.

### Action 09 — Validate the merged brief independently

1. **Goal and inputs:** inspect the exact merged revision for numerical, referential and semantic errors introduced during extraction or merging.
2. **Software work:** validate source references, identifiers, unit compatibility, conversion reversibility to the documented precision, duplicate/conflicting requirements, tolerance coverage and relationships. Compare required source claims to the brief in both directions: each requirement has a brief record; each controlling record has source/decision evidence.
3. **Reasoning work:** a review agent instance or source-reading reviewer separate from the producing/merging interpretation rereads the original source against the merged brief for initial interpretation, changed semantic mappings and candidate merges. Record producer, merger and reviewer identities, actual exposed model identities and shared source/model dependencies. Check feature identity, geometric intent, scope, datum interpretation, source priority and preservation of corrections. For image evidence, review the original view and merged feature associations using a VLM; cite concrete source regions in each finding. A deterministic replay uses the independently checked expected case and its supported rules; a new semantic exception returns to independent source review.
4. **User decision:** answer only the identified questions that require a geometry, scope or tolerance decision. A test result records the check that passed or failed; acceptance remains a separate explicit decision.
5. **Output and check:** per-feature/action status with the exact test, source and result. Use `READY — source extraction` for recorded literal value/source correspondence and `READY — named geometry operation` when the feature supplies that operation's required evidence and decisions. Use `BLOCKED — named prerequisite` with the source conflict/question and exact dependent operation. Carry a controlling feature's blocked prerequisite to the placements/relations that depend on it. The brief also records the current artifact revision and source revisions.
6. **Resume condition:** correct the affected brief record through its owning action, preserve the previous revision and rerun the tests whose inputs changed. A failed semantic association reopens its source-based evaluation and any dependent merge decisions.
7. **Basis:** [implementation plan](../implementation-plan.md), verification/reproducibility requirements; OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`), measured checks and corresponding visual inspection; [CAD-01](../workflows/cad-paths.json), provenance and ambiguity checks.

### Action 10 — Deliver the brief and specify the downstream handoff

1. **Goal and inputs:** save the checked brief revision and state which subsequent actions can consume its records.
2. **Software work:** preserve the readable brief, original evidence links, source/brief hashes, candidate comparison, merge record and actual validation findings. Record completed action, input revision, output revision, software/model identity and resumption dependency.
3. **Reasoning work:** name the target representation and its required fields. A constrained sketch consumes feature/profile intent, units, geometric and dimensional constraints. CAD solid construction consumes named parts/features, their sourced dimensions and frames. A domain operation additionally consumes the domain relationships its own operation contract requires.
4. **Handoff checks:** link each next action to the feature records it needs, its applicable tolerances and its later geometry measurement plan. Retain original source wording and proposal/decision statuses. Check that the consumer receives a single identified brief revision.
5. **User decision:** the next modeling action follows the specific task authorization and chosen output. This brief's delivery records the current documentation result and source decisions.
6. **Output and resume condition:** one documented brief revision and a named next action or exact input request for each feature branch. A subsequent source change starts from Action 01's revision step and invalidates only the affected downstream records.
7. **Basis:** [CAD-09/CAD-10 — Constrained sketch/kernel solid operations](../workflows/cad-paths.json); [DOM-04/DOM-40 — Native CAD/script-parametric authoring](../workflows/domain-paths.json); [implementation plan](../implementation-plan.md), source ownership and verification.

## 8. Local computing, remote inference and manual effort

1. **Local computing:** source reading, hashing, parsing structured records, unit normalization, candidate comparison and reference validation. Record elapsed time, input size, process memory and software version during future runs. The cost scales with source length, record count, branch count and repeated revisions.
2. **Remote inference:** reasoning over prose, cross-reference interpretation and VLM evaluation of supplied images when a remotely hosted model is used. Record the exact submitted source subset, actual model identity when available, requested configuration, call count, usage/cost where exposed, elapsed time and retries. Local processing and remote inference receive separate records.
3. **Local model inference option:** an authorized locally available language/vision model can perform a candidate or evaluation role if its checked cases support that role. Record model/weights version, context/image limits, device and memory measurements. Local-model capability and hardware demand are experiment questions until a concrete configuration is exercised.
4. **Manual effort:** source preparation, source-region checks, correction of interpretation errors and user decisions. Record the actions performed, active review time where observed, questions asked and fields changed by review. Avoid converting a nominal workflow rating into an observed duration.
5. **Mode and branch comparison:** compare agent-led, hybrid, software-first and deterministic cases on the same checked source revision. Each candidate branch records intended use, source subset, required coverage/detail and feature accuracy criteria alongside source/value fidelity, missed/incorrect feature associations, unresolved conflicts, required decisions, inference use, local runtime and manual corrections. Compare both the common requested records and each branch's additional declared target; a branch's extra detail retains its own source and resource evidence.
6. **Existing rating relationship:** [CAD-R01](../workflows/details/cad-r01.md) and [DOM-R01](../workflows/details/dom-r01.md) rate complete downstream routes under their stated conditions. This point's measured resource record concerns brief preparation and validation.

## 9. Failure and resume requirements

| Observed condition during a future run | Preserved result | Required next action and resume point |
| --- | --- | --- |
| Conflicting source values or feature meanings | Both source claims, candidate interpretations and affected feature references | Obtain the exact source-priority/design decision; repeat Actions 03–09 for affected records |
| Missing source unit/datum needed by an action | Original value/statement and the exact dependency | Obtain that unit/datum; resume Action 05 for the dependent records |
| Illegible annotation or uncertain label association | Original image/page, region reference and competing readings | Obtain clarification or a readable source; repeat extraction and evidence evaluation |
| Parser rejects a value or source format | Original bytes, location, parser/version and error | Route the record to interpretation review; retain the parser result for future adapter development |
| Agent/model response interrupted or completion uncertain | Frozen source revision, request identity, any response identity/bytes, completed candidate records and action position | Reconcile the request with the provider's available operation/response record before retrying; retain an unresolved completion as such. A retry records its own identity and relationship to the previous request; validate one identified candidate result before evaluation |
| Malformed response or partial output write | Original response bytes, parser/write error, last complete artifact revision and temporary/partial artifact identity | Recheck source digests, resume from the last complete action and validate the replacement candidate before publishing its revision |
| Candidate branches use different source revisions | Each candidate and its actual source revision | Regenerate or reevaluate affected records against the common selected source revision before merging |
| Merge creates incompatible frames or component references | Candidate records, selection decisions and exact failed references | Reopen the relevant mapping/selection; repeat Actions 05, 08 and 09 |
| Post-merge numerical or semantic check fails | Merged revision, failed check and supporting evidence | Return to the owning extraction/interpretation action, make a new brief revision and rerun affected checks |
| Source changes after a brief was checked or during interruption | Original brief/check results, recorded source digest and new source revision | Recheck source digests at resume, compare revisions, invalidate affected dependencies and resume from their first changed action |

## 10. Development specifications

The following components are proposals for future implementation. Their requirements extend the [implementation plan](../implementation-plan.md), while reusing the OCS skill (`${CODEX_HOME}/skills/ocs-engineering/SKILL.md`) and its model-contract reference (`${CODEX_HOME}/skills/ocs-engineering/references/model-contract.md`).

1. **Model-brief skill:** guide Actions 01–10; recognize the four execution modes; identify the exact source spans; classify claims, decisions and proposals; ask open questions for blocking ambiguities; retain candidate alternatives; produce a source-based evaluation and handoff. Its references should contain the tolerance distinctions, per-action evidence requirements and checked case histories. Its supported scope should name the input conditions exercised by tests.
2. **Source-intake helper:** read supported source formats, preserve original bytes/locations and identity, record hashes/revisions, expose source spans and report parsing failures. Required behavior includes stable source-location references, preservation of exact numeric/unit/tolerance text, duplicate JSON-name detection, nonfinite-number rejection and recorded CSV encoding/dialect. A new source format uses exception review until its adapter passes checked cases.
3. **Quantity-normalization helper:** normalize explicitly supported units and decimal values; retain source form, conversion rule, source/target unit and quantity type. It must preserve inequality direction and asymmetric limits, report incompatible quantity types and require explicit frame mappings for coordinate conversion. Select and document the underlying unit library or approved mapping during implementation research.
4. **Candidate-comparison helper:** compare source coverage, component/feature identity, explicit values, units, frames, tolerance applicability and dependencies. It must produce record-level disagreements suitable for source-based agent/VLM review. Comparison output retains candidate identity and input revision.
5. **Evaluation/merge controller:** assign isolated candidates, collect evidence assessments, record selection reasons, retain conflicts and combine compatible records. It must require the same source revision and prevent concurrent writes to the merged brief. A restart must recover the last complete candidate/evaluation/merge action using existing output identities.
6. **Brief validator:** verify referential integrity, unit conversion, tolerance applicability, dependency completeness and requirement coverage. It must distinguish deterministic findings from semantic review findings and tie each to the brief revision. It records concrete failed predicates and routes affected records to their owning action.
7. **Downstream handoff helper:** select the brief records required by the target geometry operation; preserve feature/source identities, units, frames, tolerance requirements and evidence status. The OCS numerical-check adapter must explicitly map the supported point/axis/plane subset and its global tolerance interface. Model readback supplies later measurement evidence with document/revision/handles.
8. **Execution record:** retain actual model/software identity, requested dispatch configuration, source revisions, completed actions, output revisions, failures, retries, inference/resource observations and active manual work. A resumed execution appends its actual result and preserves prior findings.

## 11. Meaningful future test cases

The test sources and expected findings must be checked by a source-reading reviewer before they become the expected results. Use retained project cases or purpose-built text/table fixtures whose values and expected associations are explicitly supplied. This document defines the cases without introducing model dimensions or numerical tolerances.

1. **Unambiguous structured input:** supply explicit component/feature identifiers, dimensions, units, frames and tolerances. The software-first mode must preserve every source claim and create the expected handoff without semantic corrections. Compare its result with the independently checked brief.
2. **Ambiguous description:** supply a description where one reference plausibly identifies two features. The agent-led mode must retain both interpretations, identify the exact ambiguity and ask the source-specific question before enabling the dependent geometry action.
3. **Provenance and correction sequence:** supply an initial value plus an explicit correction affecting one feature. Every mode must use the correction within its stated scope, retain the earlier source and preserve unrelated values.
4. **Mixed units and tolerance forms:** supply compatible units, symmetric and asymmetric limits, and minimum/maximum constraints. Normalization must preserve the expected quantities and acceptance intervals and retain original forms. Include an incompatible quantity/unit pair that must produce the expected error.
5. **Source uncertainty, geometric allowance and numerical comparison threshold:** supply a measured value with uncertainty, a separately stated geometry tolerance and a separately stated numerical comparison threshold, each with its own source. Normalization and merge must preserve all three and use the intended field in the downstream check specification. When solver stopping or export/readback criteria apply, preserve their separate sources and roles as well.
6. **Frame and datum interpretation:** supply feature positions in named frames and one unresolved relative direction. Valid mappings must preserve the expected reference; the ambiguous direction must produce its exact dependency question. Include a conflicting source frame as a failure case.
7. **Visual label association:** supply an image with an explicit value label and two nearby candidate features, plus an independently checked association. The VLM must cite the actual source region and meaning; the software comparison must preserve the exact value. Record incorrect associations and manual corrections.
8. **Parallel evidence merge:** supply candidate branches with complementary records, one wrong feature association and one conflicting value. The final brief must combine compatible records, select associations using cited evidence and preserve the conflict until resolved. Rerun the full numerical and semantic checks on the merged result.
9. **Coverage and invented-claim detection:** omit a required source claim in one candidate and add an unsupported value in another. Validation must identify the named omission and the unsupported added record using the two-direction source comparison.
10. **Interrupted run and changed source:** stop a branch after a completed action, then resume with the same sources; separately revise one source before resuming. Include an uncertain remote completion, malformed response and partially written candidate. The run must reconcile request/response identities, recheck source digests, reuse complete work only for matching source revisions and reevaluate dependent records after a change.
11. **Per-feature OCS check mapping:** provide feature requirements using different tolerance pairs and a requirement outside the existing checker's supported kinds. A later adapter must retain each feature's rule, form valid supported groups and report the unsupported mapping with its feature identity.
12. **Known-format replay:** repeat a checked deterministic case with identical input/configuration revisions. Compare its semantic content, source associations and validation results. Then alter one supported source value and verify the resulting change set and dependency invalidation.
13. **Parser source-loss cases:** supply duplicate JSON object names, `NaN`/infinite tokens, a finite token that exceeds the selected numeric representation, a CSV quoting/dialect mismatch and decimal strings whose binary-float intermediate would change their exact representation. The intake must retain the original source, detect the named error before value loss and either preserve the required decimal representation or report its supported numeric limit.

## 12. Migration from agent actions to tested software

1. **Collect checked actions:** retain actual agent decisions and intermediate records from exercised cases. Name the repeated operation, its inputs, source conditions, exceptions, outputs and manual corrections.
2. **Separate fixed rules from interpretation:** propose software for an action whose required rule can be stated precisely, such as parsing a known column, converting a supported unit or checking a source reference. Retain reasoning review for the specific meanings and exceptions that required source interpretation.
3. **Define expected behavior:** use reviewed source cases and their expected values, associations, conflicts and questions. Include cases outside the proposed supported subset and specify the exception result.
4. **Implement the smallest reusable helper:** use existing suitable libraries and preserve their licences. Keep the helper's supported formats, unit rules and semantic assumptions explicit. Integrate it at the owning action in this procedure.
5. **Compare on held-out cases:** keep some checked cases separate from helper development. Run the agent-assisted baseline and software candidate on the same source revisions; compare source fidelity, associations, failed checks, exceptions, manual corrections and resource use.
6. **Promote only the checked subset:** after the applicable cases pass, record the helper/version, supported input conditions and test evidence. Route exceptions to the relevant agent/user action. A tested promotion changes the execution mode of that action; its source, tolerance and validation duties remain explicit.
7. **Extend from observed failures:** retain a new failure as a source-linked case, correct its expected interpretation through review and add a targeted test before extending the helper's supported subset. Repeat post-merge validation whenever its outputs change.
