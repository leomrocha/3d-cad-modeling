# Documentary verification method

Date: 12 November 2026. This method checks the written audit outputs. Independent review supplies the separate examination of source meaning, software capabilities and proposed procedures.

1. **Operation coverage:** compare each point's operation IDs with its assignment in [sequence.json](/home/leo/projects/3dmodeling/research/action-audit/sequence.json). Require exactly the assigned set, unique IDs and at least three concrete actions per operation. The first-point document has ten actions shared by its two intake operations.
2. **Action records:** require each action's ID/name and the fifteen nonempty fields in [the plan](/home/leo/projects/3dmodeling/research/action-audit/plan.md): purpose, intended use, inputs, outputs, accuracy, evidence, software, agent, user decisions, dependencies, proposed development, procedure, validation, failure/resume and resources. Check agent-led, hybrid, software-first and deterministic options, source references, alternatives, merging, software migration and future tests for every operation.
3. **Substantive review:** the separate reviewer reads the operation/action contracts, readable procedure, original records and software/visual/source findings. The reviewer records specific findings, receives targeted designer repairs, rereads the changed sections and records observed dispositions. A complete field is a structural result; the review assesses its content.
4. **Sources:** register original external URLs at their actual inspection status and retain current local-file hashes for each point. Recompute the current point's hashes before reporting a match. Older snapshot observations remain historical records with their original dates and hashes.
5. **Links and document syntax:** parse research JSON; check newly authored local Markdown links are absolute and resolve; require a final newline and reject an extra blank line at the end of the point documents. Source URLs used by the new documents/action contracts must exist in the source register.
6. **Preservation:** compare project instructions, original implementation plan, original operation/recipe input files, original ranking tables, first-point procedure and historical cleanup receipt against the sequence checkpoint. Extract original Mermaid blocks with the pattern ` ```mermaid\b.*?``` ` using the regular expression word boundary, assert a positive block count, and compare their text with current files.
7. **Documentation builders:** execute `python3 research/tools/build_workflow_register.py --date 2026-11-12` and `python3 research/tools/build_workflow_details.py --date 2026-11-12`. Require successful exit and empty error lists. Hash all research Markdown and JSON files, run the builders again and compare hashes. Write the receipt only after comparison succeeds; reparse it and repeat the comparison with the final receipt included.
8. **Git checks:** stage only the current authorized documentation batch, run `git diff --cached --check`, correct formatting within that batch when needed, refresh affected source snapshots and repeat the checks. Record any failed check and its successful rerun in the affected receipt. Commit the point before the next point begins.
9. **Result meaning:** receipts report document/source checks with their exact scope. Proposed CAD actions, helper implementations, geometry measurements and future fixtures retain their stated evidence until an actual execution provides its own run record.

Coordinator response model: `gpt-6.1-sol`, established in supplied context. Requested child configurations and reported runtime identities are recorded in the corresponding review documents.
