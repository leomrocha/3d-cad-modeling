## Proposed component responsibilities and data handoffs

The following fields describe a design contract, not an implemented schema. A source locator means the precise line, row/cell, page/region, or image coordinates needed to re-find evidence. A candidate is one independently produced interpretation with its own identity and source links.

1. **Intake and identity component.** Inputs: supplied description, dimension table and supporting references; caller-provided source path or exact URL, retrieval/observation date where applicable, content type and access terms. Outputs: immutable original reference and a source manifest with source ID, path or URL, byte hash and hash algorithm, revision where given, file size, acquisition status and relationship to derived extracts. Retain supplied exact URLs and originals. File hashes track bytes; they do not establish the truth of a source. Explicitly surface inaccessible, unreadable or changed inputs.
2. **Text and table extraction component.** Inputs: source manifest and declared source format/encoding, CSV dialect or JSON mapping; optional image/page for OCR. Outputs: raw text spans and table cells, source locators, extraction method, tool/version, source identity, and any parser errors. Preserve original strings and layout references alongside machine-readable candidates. Treat page and image coordinates with their crop/transform mapping where extraction uses a derivative. An extraction result is source text or an OCR candidate, not a feature assignment.
3. **Structural and unit checker.** Inputs: candidate records and explicitly declared source units, conversion rules and unit dimensions. Outputs: parsed numeric representation, original expression, source unit, converted value/unit and conversion rule when applicable, validation findings and blocked fields. Check required fields, allowed types, finite values, duplicate IDs, references, units and dimensional compatibility; apply value ranges only when a source or explicit requirement supplies them. Use decimal-preserving parsing where appropriate, retain original precision and record rounding. A successful structural check does not settle semantic meaning or engineering validity. A unit parser and conversion library are proposals pending selection and evidence.
4. **Semantic interpretation and provenance component.** Inputs: exact description, extract candidates and supporting references. Outputs: named component/feature, property or relationship, value, quantity type, original expression, source locator, evidence classification, derivation, actor/tool/version and ambiguity. Record frame origin, axes, datum, part boundaries, intended use and output requirements with their sources when stated. Distinguish supplied instruction, measurement, source claim, calculation, inference, assumption and unresolved question; preserve conflicting source statements. A source link is part of each claim, including any derived conversion and its inputs.
5. **Parallel candidate coordinator.** For an authorized parallel run, give separate producers the same immutable source manifest and the same declared task, with isolated output paths and distinct candidate/run IDs. Suggested roles: source-literal interpretation, software extraction, and independent feature/frame interpretation. Inputs, version/configuration, execution status and provenance accompany each result. Do not share candidate conclusions before independent production; record shared extractors or models because shared dependencies can produce correlated errors. Candidate agreement is evidence for review, not proof of correctness.
6. **VLM-led evidence merge.** The merge component reads original text, supplied images where available, individual candidate records and locators. It compares each claim to its original source, emits selected or combined claims with candidate IDs, exact source spans/regions, rationale and unresolved conflicts, and retains all candidate outputs unchanged. A text-only task still provides the original text to the selected model; image input is used when the source actually contains an image and the selected model supports it. No model or API is selected by this review. Merge cannot choose an engineering design, invent a dimension, promote inference to measurement, or silently suppress dissent. A separate checker verifies source locators, units, duplicate identities and conflicts after merge; an independent semantic reread checks feature association, frame and source meaning. Record human decisions separately from model interpretations.
7. **Brief publisher and downstream handoff.** Output: versioned source-linked model brief, source manifest, complete candidate ledger, unresolved questions, conflict/decision ledger and machine-readable check results. The handoff states which claims are usable for the intended downstream operation and which depend on unresolved ambiguity. Consumers receive original and normalized expressions, feature/frame IDs, evidence links and tolerance records. A complete structural check and a user acceptance decision are separate facts; do not mark any choice accepted without explicit `MARK AS ACCEPTED`.

## Feature-level tolerance requirements

1. Record each feature/property's nominal value and unit, source locator and evidence classification. Associate the feature and frame/datum to which the value applies. Preserve asymmetric limits, conditions, fits or other notation exactly when supplied.
2. Keep three concepts in distinct fields: **engineering allowance**, the permitted variation explicitly specified for the feature; **measurement uncertainty**, the stated uncertainty of a measurement; **computational comparison tolerance**, the numerical threshold later used by a particular check. Each needs its value, unit, source or explicit derivation, applicability and status. These quantities can have different meanings and must not be silently substituted for each other.
3. Missing source evidence for a tolerance produces an unresolved check requirement; do not assign a universal tolerance. The future check adapter must bind each check to its feature, measured property, source revision, units and applicable threshold. The OCS checker's global tolerances are a constraint of each invocation, not an adopted project-wide tolerance.

## Failure and resume behavior

1. Missing or changed source bytes, ambiguous encoding/dialect, malformed table, unsupported file, unknown unit or invalid value: retain original and partial extraction; record exact source ID, stage, error and affected candidates; stop dependent claims while allowing independent source records to finish. Recheck hashes before resuming.
2. Conflicting values, feature associations, frames, units or revisions: retain every evidence-linked alternative with its origin and scope; mark dependent claims unresolved. Do not resolve by majority vote, score or source order. Resume only affected derivations after a sourced resolution, and record that resolution and actor.
3. Producer failure or partial output: record run identity, inputs/hashes, tool/version/configuration, finished artifacts and state; retain successful independent candidates. Resume or rerun the failed producer under a new recorded attempt linked to the same inputs; do not overwrite earlier outputs. Changed input creates a new source revision and invalidates affected derived claims.
4. Merge interruption or invalid structured response: retain raw response and completed candidate artifacts, record the attempt and exact validation errors, and produce no completed brief for the affected claims. Resume from the last validated boundary with the same input identities. If an external model service is used later, its request identity, data exposure and response status must be recorded; uncertain completion needs service-specific reconciliation before retry.

## Meaningful future tests

1. Use source fixtures containing quoted CSV fields, decimal separators, duplicate IDs, text spans, mixed units, a changed source file and an unreadable reference. Check exact provenance, byte-identity change detection, retained originals, parsing diagnostics and deterministic repeatability of structural checks.
2. Use fixtures with a source-linked feature dimension, an asymmetric engineering limit, a separately stated measurement uncertainty and a separate check threshold. Verify their association survives conversion and merging; remove one source or unit and verify a specific unresolved result rather than a default.
3. Give candidate producers contradictory values, different feature associations and a shared extraction error. Check that the VLM-led merge cites the original evidence, retains dissent and does not treat agreement as proof; independently inspect the semantic result against a held-out source. Include a deliberately misleading OCR candidate with its source crop.
4. Interrupt extraction and merge after partial artifacts are written; verify resumable state, no overwrite, no silent input change, and preservation of successful independent candidates. Verify that a new source revision invalidates affected derived records.
5. For the later OCS adapter only, use supplied synthetic point/axis/plane observations with known outcomes, incorrect provenance fields, duplicate checks and explicitly different feature tolerances; verify each mapping and report the checker's limited scope. This test checks software behavior on the fixture, not physical capacity or author acceptance.
