## Concrete operation findings and proposed interfaces

1. **DOM-08 — CAD assembly to articulated robot structure.** `map_robot(cad_assembly, joint_set, measurements) -> robot_assembly, mapping_report` groups named CAD occurrences into rigid links using reviewed mappings, retains source revision and occurrence placements, and associates each joint with parent and child link, type, origin, axis, limits and source. Detect disconnected nodes, multiple parents, duplicate IDs, graph cycles and inconsistent units/frames. A tree and a closed-loop assembly are different graph classes: retain the loop in the assembly graph and report the target export's supported representation rather than silently deleting its closure. Assembly CAD constraints are evidence of geometry and relationships; interpreting them as intended robot joints needs review. [FreeCAD Assembly documentation](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Assembly_Workbench.md) documents assembly authoring; [ROS URDF tutorial](https://github.com/ros/urdf_tutorial) covers link and joint descriptions. Neither source record demonstrates a general CAD-to-robot adapter.
2. **DOM-09 — Robot assembly to URDF package.** The registered contract has common inputs `robot-assembly`, `joint-set`, `mass-properties`, plus one of `visual-scene` or `collision-set`. `export_urdf(robot_assembly, joints, mass_properties, visual_or_collision) -> urdf, mesh_assets, mapping, report` is a proposed boundary for a rooted supported tree with resolved joint frames, axes, types and appropriate limits, physical values, asset paths and conversions. A visual scene alone must not be treated as a collision set, or vice versa; report which roles exist and which a downstream consumer requires. Preserve source mesh frames and map link IDs and visual/collision/inertial origins separately. Fixed, continuous and movable joints need type-specific limit validation; the contract's general “limits” field does not imply that every joint has finite lower/upper travel. For loops, report the edge and route to a representation supporting the required closure; a tree-only URDF exporter cannot silently change the mechanism. Parse and compare forward-kinematic fixtures and import in the chosen target consumer. [URDF tutorial](https://github.com/ros/urdf_tutorial) describes link/joint/visual/collision/inertial roles; [URDF consumer description](https://choreonoid.org/en/documents/latest/handling-models/modelfile/modelfile-urdf.html) is registered from an existing report, not verified locally here.
3. **DOM-10 — URDF import and MJCF conversion.** `import_urdf(urdf, assets, mujoco_version) -> editable_spec_or_error, import_report`; a distinct `compile(spec_or_xml) -> compiled_model_or_error`; and `serialize_mjcf(spec_or_model, destination) -> mjcf_or_error, loss_report` are proposed stages. The project source record describes `MjSpec` XML/URDF parsing and compile and `MjModel.from_xml_path` parsing/compiling XML or MJZ; it does not by itself establish the exact serialization method, its version or supported preservation. Compilation success yields a compiled model, and the registered output is an MJCF artifact: require the serialization stage and a reopened artifact with explicit field/default/loss mapping. URDF importer options, asset paths, fixed-joint treatment, visual handling and extension parsing must be checked for the pinned version. Compare named link/body correspondence, transformed axes, ranges and forward kinematics, using graph mappings where compiler fusion changes counts. Actuators and contact models require sourced MJCF authoring if absent in source. [MuJoCo model editing](https://mujoco.readthedocs.io/en/stable/programming/modeledit.html) and [modeling guide](https://github.com/google-deepmind/mujoco/blob/main/doc/modeling.rst) are registered primary references; the exact XML-write API is a source lookup gap.
4. **DOM-11 — Native MJCF authoring.** `author_mjcf(robot_assembly, joints, collisions, mass_properties, materials, configuration) -> mjcf, asset_manifest, report` authors an explicit body hierarchy, geoms, joints and inertial elements plus only the requested actuator/contact information. Preserve the given domain inputs and the compiler settings: infer inertia from geoms only when deliberately selected, because changing a collision geom can otherwise change body dynamics. A closed loop requires a supported closure representation and an independently checked constraint; the body hierarchy itself remains a tree. Check asset resolution, IDs, joint axes and ranges in their declared frames, inertial fields and declared actuator/sensor/contact parameters. Source: [MJCF XML reference](https://mujoco.readthedocs.io/en/latest/XMLreference.html), [MuJoCo model editing](https://mujoco.readthedocs.io/en/stable/programming/modeledit.html). Verify exact equality-constraint semantics and representation against the pinned version before specifying a particular loop adapter.
5. **DOM-12 — MuJoCo mesh assets.** The registered alternatives are one of `cad-solid`, `b-rep`, `visual-scene`, or `robot-assembly`. `tessellate(source, occurrence_selection, source_frame, target_frame, tolerance, format) -> meshes, manifest, report` needs a selected supported geometry occurrence; a scene or assembly input does not imply a single mesh or single link. Retain source hash, units, transform direction, tessellation settings, per-part/link association and mesh role. Compare source and output bounds and selected interfaces, face orientation and units. Geometry may need conversion to a target-supported mesh encoding; the operation's OBJ and binary STL source claim must be checked against the selected MuJoCo version and parser. [MuJoCo overview](https://github.com/google-deepmind/mujoco/blob/main/doc/overview.rst), [plugin documentation](https://github.com/google-deepmind/mujoco/blob/main/doc/programming/extension.rst).
6. **DOM-13 — Convex collision sets.** `decompose_collision(mesh, link_or_environment_id, mesh_to_target_frame, parameters, tool_version) -> collision_set, manifest, approximation_report` emits individual pieces associated with the correct link/body or static environment frame, with source hash, scale, per-piece transform, tool/version and parameters. Decompose each moving link independently rather than flattening the complete articulated assembly into one collision object. Compare directional envelope error, relevant holes and passages, and intended contact cases; volume or a bounding box alone does not establish shape coverage. Distinguish render geoms, collision geoms and inference of mass. [CoACD repository](https://github.com/SarahWeiii/CoACD) is registered as an existing-report claim for decomposition and CLI; [V-HACD README](https://github.com/kmammou/v-hacd/blob/master/README.md) is previously web-inspected and records archived/end-of-life status. The local [DOM-R02 dossier](../../workflows/details/dom-r02.md) has both `-i/-o --threshold` and `--input/--output` example spellings and asks for pinned CLI confirmation; neither spelling is established by this review.
7. **DOM-14 — Calculate or import physical mass properties.** Registered alternatives are `physical-measurement-set` alone, or `material-set` together with one of `cad-solid`, `b-rep`, `mesh`, `cad-assembly`. `mass_properties(measurements_or_geometry_materials, frame, method) -> properties_with_field_status, report` preserves mass, COM and inertia individually with reference frame, units and evidence. A measured scalar mass alone supports a mass field; it cannot determine COM or inertia. Geometry plus density supports a calculation only for an appropriate valid representation and distribution assumption; visually assigned material is not a density measurement. For each link, translate inertia from a named reference point to COM using the parallel-axis theorem, rotate into the target inertial axes and apply length/mass conversion consistently (inertia dimensions mass × length²). Check symmetry, positive eigenvalues and principal-moment triangle inequalities within numerical tolerance, plus explicit target format requirements; physically admissible numbers still do not establish measured physical accuracy. [Implementation plan](../../implementation-plan.md), [MuJoCo XML reference](https://mujoco.readthedocs.io/en/latest/XMLreference.html). Exact MJCF `fullinertia`/`diaginertia` interpretation and compiler adjustments require the pinned primary documentation.
8. **DOM-15 — Semantic IFC building.** `author_ifc(brief, element_records, unit_context, frame_context) -> ifc, mapping, validation_report` uses explicit element classes, containment/aggregation, project units, geometric contexts, placements, property and material assignments; preserve declared source and stable identity mappings. A geometry shape alone does not determine its IFC class or spatial relationship. The registered brief is the operation input: its required semantic/geometry fields must be present or supplied as explicitly linked dependencies, rather than invented. [IfcOpenShell code examples](https://docs.ifcopenshell.org/ifcopenshell-python/code_examples.html) describe project, units, contexts, hierarchy and wall creation; [geometry creation](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_creation.html) covers geometric representations. Openings need an opening element, appropriate geometry/placement and void relationship; filling elements require the matching relationship when present. [feature.add_feature](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/feature/add_feature/index.html) records the wall/void feature example.
9. **DOM-16 — IFC triangle extraction.** `extract_triangles(ifc, element_selection, geometry_settings) -> mesh, element_map, report` is scoped to triangles; record IFC schema, source hash, selected elements, GlobalIds, material/item mappings where available, opening behavior, local-to-world transforms and output units. Compare independently selected bounds and placements. [IfcOpenShell geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html) and [geometry API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/geom/index.html) are registered sources. The operation's `changes_or_infers` also mentions B-rep output, while its output is `mesh` and DOM-27 separately owns B-rep extraction: preserve both contracts and label B-rep as an alternative route, rather than claim it is a DOM-16 output. Confirm exact iterator settings and units, placement application and opening subtraction at the pinned version.
10. **DOM-17 — IFC to GLB visual scene.** `ifc_to_glb(ifc, selection, unit_axis_mapping, id_policy) -> glb_scene, sidecar, report` needs a verified adapter chain, source and output hashes, element-to-node mapping, transform convention, units and chosen material treatment. A sidecar preserves selected IFC IDs/properties; preserve the IFC for relationships and original property sets. Verify identity coverage including absent geometry, opening shapes and repeated instances, world bounds and orientation after independent reopen. [Blender pipeline](https://www.blender.org/features/pipeline/) establishes format support at a general level, and the local prior provenance example (`${ENERGY_SIM_ROOT}/data/real-house-ifc/provenance.json`) is a domain-specific pattern, not proof of a generic conversion. Exact IfcConvert GLB support and ID mapping need version-specific primary-source confirmation; a chain through Blender is a distinct proposed adapter.
11. **DOM-24 — Blender scene assembly.** The registered alternatives each independently accept `cad-solid`, `mesh`, `ifc`, `robot-assembly`, or `camera-solution`. `build_scene(input_variant, import_mapping, units_frames, scene_policy) -> visual_scene, manifest, report` may create a camera-only scene when given only a camera solution; require geometry only for outputs or checks that actually use it. Supported import of each input class requires a real adapter and its version; a scene object map and parent/world transforms preserve traceability but do not reproduce IFC semantics, robot dynamics or editable CAD history. A Blender background Python entry point is documented by the [Blender command-line manual](https://docs.blender.org/manual/en/latest/advanced/command_line/). [Existing local research](../../domains-and-components.md) reports Blender 5.0.1 and Blender Lab MCP requiring 5.1+ at its observation date; recheck the live version before using that bridge.
12. **DOM-25 — Fabrication package.** The registered common inputs are `dimensions` and `material-set`, plus one of `cad-solid` or `cad-assembly`. `package_fabrication(model_revision, dimensions, material_set, process_requirements, output_targets) -> files, manifest, check_report` relates each drawing dimension, tolerance, material, part/occurrence and selected process to source/revision. Confirm actual output capability and reopen exported files in the designated receiving application; carry annotations separately if the neutral export omits them. Geometry, dimensions and a material record alone do not supply a complete process specification or prove manufacturability. [Implementation plan](../../implementation-plan.md) and [CAD research](../../cad-and-skills.md) describe proposed outputs, not a demonstrated project package exporter. OCS is the baseline; inspect its actual supported drawing/export APIs before promising a function.
13. **DOM-27 — IFC OpenCASCADE B-rep extraction.** `extract_brep(ifc, element_selection, kernel_settings) -> breps, id_placement_map, report` is a distinct path from DOM-16 triangles. A B-rep output describes the geometry produced by the selected kernel for the given representation; retain source identity, placements, units and mappings, and check topology and face types. A B-rep can contain planar or faceted geometry, so do not claim that conversion restores analytic surface intent or authoring history. Confirm the exact `create_shape`/iterator configuration, PythonOCC dependency and transform behavior for the selected build against [geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html) and [geometry API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/geom/index.html).
14. **DOM-31 — Assembly graph and joint set.** `author_graph(cad_assembly, measurements, brief, reviewed_relations) -> assembly_graph, joint_set, issues` retains part occurrence IDs, separate transforms and explicit evidence per connection; graph traversal checks roots, connectivity, duplicate parents and loops, without interpreting shape as intended motion. For movable axes, include coordinate frame, direction and units; retain limits only where appropriate to the joint type. Closed loops remain explicit graph edges. Source: [FreeCAD Assembly Workbench](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Assembly_Workbench.md), [ROS URDF tutorial](https://github.com/ros/urdf_tutorial). These sources do not establish the proposed canonical graph implementation.
15. **DOM-32 — Map CAD geometry into an existing MJCF tree.** `map_geometry(existing_mjcf, cad_assembly, joints, measurements, component_record, body_map) -> updated_mjcf, mapping, report` requires reviewed CAD-part-to-body mapping, asset rights and mesh-to-body transforms. Preserve existing body/joint topology, actuator and sensor declarations and source revision. Geometry roles must be explicit and any change in geom-derived mass/inertia must be identified; compiler defaults or geom replacement can affect physical properties even when body and joint XML is unchanged. Compare compiled model and serialized declarations, asset references, transforms and FK with the source; retain original and report differences. If preserving the original behavior requires extra conditions, surface them rather than quietly switching to a rebuilt model. Sources: [MuJoCo modeling guide](https://github.com/google-deepmind/mujoco/blob/main/doc/modeling.rst), [XML reference](https://mujoco.readthedocs.io/en/latest/XMLreference.html).
16. **DOM-33 — Add environment collisions to an existing MJCF.** `add_environment(mjcf, mesh, collision_set, scene_transform) -> updated_mjcf, manifest, report` adds named static environment geoms and the registered environment transform while preserving the existing robot graph. Compare exact source/target scene frames, pose and units; check contact filters, bounds and intended open passages using named fixtures. Record visual and collision geometry separately and each convex piece's transform. A compile check establishes model load, not correct scene alignment or contact response. [MuJoCo overview](https://github.com/google-deepmind/mujoco/blob/main/doc/overview.rst), [XML reference](https://mujoco.readthedocs.io/en/latest/XMLreference.html).

Record element coverage, omitted elements and approximations; collision pieces must retain independently placed local frames and preserve required passages. Compare world geometry and named contact fixtures; a MuJoCo world is a simulation derivative and the semantic source remains IFC. [IfcOpenShell geometry API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/geom/index.html), [MuJoCo modeling guide](https://github.com/google-deepmind/mujoco/blob/main/doc/modeling.rst).
18. **DOM-35 — Place a library component in semantic IFC.** `place_component(ifc, component_record, measurements, target_class, target_placement) -> ifc_revision, identity_map, report` selects a supported representation adapter, preserves exact asset bytes/rights and source ID, assigns an IFC class/representation and a spatial relation, and uses a documented project/unit-to-placement transform. Verify mapped occurrence placement, stable IDs for existing elements, relationship and representation validity, and asset licence per item. The [IfcOpenShell geometry creation guide](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_creation.html) documents IFC representation creation, and the [FreeCAD library](https://github.com/FreeCAD/FreeCAD-library) is a source collection; neither source establishes automatic conversion of every library format and meaning into IFC. 19. **DOM-37 — Robot assembly from a CAD component.** `create_robot_occurrence(cad_solid, measurements, brief, component_record, reviewed_attachment) -> cad_assembly, assembly_graph, joint_set, report` retains source component identity and units, instantiates an occurrence and creates a parent attachment and joint from explicit frame/motion evidence. A single solid input can be instantiated as one occurrence; the proposed parent and desired connection must be supplied by the brief and supporting data. If missing, return an unresolved issue and partial evidence rather than fabricate the parent or joint. Verify interface positions, frame transforms, axis and type-specific range; [FreeCAD Assembly Workbench](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Assembly_Workbench.md) documents assembly joints and [ROS URDF tutorial](https://github.com/ros/urdf_tutorial) documents the downstream descriptions.

## Units, frames and evidence contract

1. Each transform identifies source and target frame, source/target revisions, orientation and units; use one explicit matrix convention, e.g. `p_target = T_target_source p_source`. A rigid transform and a unit scale are recorded separately. Check joint axis orientation in the appropriate joint/body frame; compare forward kinematics at named configurations, including finite range boundaries when the joint has them.
2. Each inertial record identifies mass, COM position, inertia tensor, reference point, orientation frame, units and provenance independently. A tensor represented about a different origin must be shifted before comparison; a changed frame requires rotation; mm² to m² is part of inertia conversion. In MJCF, confirm whether a full tensor is diagonalized and which frame is encoded in the actual selected API/version before serializing. Keep visual, collision and inertial roles as distinct records even if their geometry coincides.
3. IFC project units, element local placements, spatial hierarchy and any map/CRS conversion are separate records. [unit.assign_unit](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/unit/assign_unit/index.html) documents project units; [edit_object_placement](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/geometry/edit_object_placement/index.html) is recorded as a 4×4 placement API with an `is_si` translation setting; [georeference API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/georeference/index.html) uses supplied CRS/map values. Confirm geometry-extraction output units and whether placements are baked for the actual selected settings before composing transforms, to avoid a double transform or double unit conversion.
4. Existing source claims, locally inspected project documents, source calculations, assumptions and later test results retain separate labels. A compile, schema validation or runtime contact fixture verifies a specific artifact and operation; it does not establish physical measurements, dynamic performance or author acceptance. The OCS model contract (`${CODEX_HOME}/skills/ocs-engineering/references/model-contract.md`) checks supplied point/axis/plane numbers and is not a live CAD query or solid validation.

## Proposed future tests; none executed in this review

1. **Tree and loop:** A two-link fixture with a named fixed base, rotated joint frame, known axis and range produces matching link poses at named configurations. Duplicate parents, disconnected links, reversed axes and an invalid or unknown range produce exact findings. A four-bar loop retains its closure edge; a tree-only export reports the unsupported edge, and a supported closure adapter checks constraint consistency.
2. **URDF import and MJCF:** A package with per-link visual/collision origins, units, fixed and movable joints, inertial tensors and relative assets passes source parse, target compile, serialized MJCF reopen and source-to-target FK checks. An unresolved asset, unsupported element, dropped or defaulted field, compiler-fixed-body fusion and invalid MuJoCo extension each produce specific output; successful compile alone cannot satisfy the serialized MJCF output.
3. **Inertia:** A body with independently specified mass, COM and a rotated tensor about a displaced reference has expected converted COM/tensor in the target frame. Check an invalid negative principal moment, triangle-inequality violation, mistaken mm² scaling, incorrect parallel-axis sign and a scalar-mass-only measurement; the last reports COM and inertia as separate missing fields rather than inventing values.
4. **Meshes and contacts:** Two independently moving links with concave collision shapes, separate local transforms and one narrow passage yield per-link hull sets and correct named open/blocked contact fixtures. Wrong unit scale, merged moving links, an overfilled passage, inverted frame and invalid mesh report failure or unsupported input; preserve source mesh and all failed approximations.
5. **IFC:** A project with explicit units, storey, rotated wall, host opening and filling element produces correct containment/void/filling relations and known world placements. Extract triangle and B-rep outputs separately, compare element mappings, bounds and opening geometry, and reopen a GLB derivative. Exercise millimetre/metre conversion, local versus world geometry, missing representation, duplicate ID, incorrect opening transform and double-applied placement. Check the chosen consumer and versions, geometry settings, and semantic sidecar separately.
6. **Scene, library and fabrication:** A camera-only input succeeds as a camera-only Blender scene; unsupported CAD input or an unresolved adapter returns an explicit error. Two distinct placements of one library component retain occurrence and source identities. A fabrication package includes linked drawing/model revisions and reports a missing tolerance or receiver-reopen failure. Include asset rights and source/output hashes in each manifest.
7. **Existing MJCF modification:** Replace one mapped visual geom and separately one collision geom in a model with explicit joints, actuator and sensor. Compare source and result declarations, body/joint transforms, actuator/sensor presence and inertial values. A changed inferred inertia or missing asset is a surfaced difference; a topology change violates DOM-32's preservation requirement.

Evidence: [Luna primary-source review](point-06-sources.md) and [source records](../../sources/round-05/point-06-web-sources.json) record 18 previously web-inspected original pages and four failed accesses. The following are documentation claims, not local implementation, runtime tests or author decisions. Earlier requests for primary-source lookup remain applicable to the selected pinned version, except for the source questions resolved here.

1. **DOM-10/11/32/33/34 — MuJoCo parse, compile and save.** [Model editing](https://mujoco.readthedocs.io/en/stable/programming/modeledit.html) documents `MjSpec.from_file()` and `from_string()` as parsing interfaces; `mj_compile` compiles an editable spec into `mjModel`, while `MjModel.from_xml_path()` combines parsing and compilation. `mj_saveXML`, `mj_saveXMLString`, or `mj_encode(..., ".xml", ...)` serialize a spec as MJCF; XML encoding flattens it. A supplied compiled model can copy changed model values into the spec first. The documented `compiler/savecompiled` default is `true`, which saves compilation-made values in canonical form; `false` saves parsed/authored values without requiring compilation. Serialization omits or expands original textual constructs including later file comments, includes, replicate, flexcomp, attach and actuator shortcuts; preserve the original and report these losses. Verify exact behavior against the selected version.
2. **DOM-09/10/11 — Units, frames and effective defaults.** The [MuJoCo XML reference](https://mujoco.readthedocs.io/en/stable/XMLreference.html) documents no imposed physical unit system, MJCF angle default degrees and URDF angles in radians. URDF compiler defaults include `discardvisual=true` and `fusestatic=true`: the former may discard visual-only geoms and the latter can alter body counts while preserving documented kinematics and dynamics. MJCF body hierarchy is a tree; `connect` or `weld` equality constraints express particular extra relations, with their own semantics and solver behavior. Preserve the source closure edge and verify the chosen mapping. The [URDF joint model](https://github.com/ros/urdfdom_headers/blob/rolling/include/urdf_model/joint.hpp) defines the parent-to-joint transform, with child link frame equal to the joint frame; its axis meaning depends on joint type.
3. **DOM-11/12/14/32 — Inertial and mesh transforms.** The [MJCF XML reference](https://mujoco.readthedocs.io/en/stable/XMLreference.html) defines the inertial frame at the centre of mass with principal axes. `fullinertia` order is `M11, M22, M33, M12, M13, M23`; compilation diagonalizes the matrix and sets inertial orientation/diagonal values. Non-positive eigenvalues are rejected unless a positive `boundinertia` supplies a lower bound. `inertiafromgeom=auto` infers only when the body lacks an inertial element; `true` overrides explicit inertia. The documented mesh formats include OBJ, STL and MSH. The compiler recentres and reorients mesh assets; inspect `mjModel.mesh_pos`, `mesh_quat` and `mesh_scale` and compose the effective mesh, geom, body and world transforms when comparing placed geometry. Source geometry, collision approximation and inertia mode are separately recorded.
4. **DOM-13 — CoACD command-line syntax.** The current [CoACD README](https://github.com/SarahWeiii/CoACD) documents both forms as aliases: `-i/--input` and `-o/--output`; `-sp/--split` additionally emits individual convex components into an output-parts directory. `-t/--threshold` defaults to 0.05 in the documented normalized metric; `-rm/--real-metric` uses metre-valued thresholds and requires metre-scale input. `--max-convex-hull` requires merge and can exceed the threshold. This resolves the earlier spelling uncertainty for that documented revision, while release-specific behavior and output are still to be checked in a future authorized run.
5. **DOM-14 — Open CASCADE mass integration.** [BRepGProp](https://occt3d.com/dev/doc/refman/html/class_b_rep_g_prop.html) documents `BRepGProp::VolumeProperties(shape, props, ...)`, which accumulates unit-density volume properties into `GProp_GProps`; a finite coherently oriented solid without free boundaries is required, and the API does not establish those conditions itself. The [GProp_GProps reference](https://dev.opencascade.org/doc/refman/html/class_g_prop___g_props.html) provides `Mass()`, `CentreOfMass()` and `MatrixOfInertia()`: the latter reports the central tensor with axes parallel to absolute Cartesian axes. `Add(component, density)` applies a density and performs the parallel-axis shift for component accumulation. Apply physical density exactly once in consistent units; rotate/shift tensors as required by assembly frames, then independently check mass and COM. `UseTriangulation` and integration tolerance select different calculation conditions; cite those settings and do not claim that the result itself measures physical material density.
6. **DOM-15/16/27/35 — IFC geometry and semantics.** IfcOpenShell 0.9.0post1 [geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html) documents `create_shape` results with local mesh vertices, triangulated faces, item/material IDs and an element transform; element-level geometry applies opening subtraction by default. `use-python-opencascade` enables a B-rep output; a geometry iterator processes whole elements and supports caching and multicore processing, while individual shape processing can select a representation/item/profile. The documentation does not attach a unit tag to Python mesh vertices: record settings and the input/output unit convention. The [add_representation API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/geometry/add_representation/index.html) accepts Blender object/data geometry and returns a shape representation or `None`; creating a product, assigning class, placement and spatial relations are separate operations.
7. **DOM-17 — GLB and coordinates.** The [IfcConvert usage](https://docs.ifcopenshell.org/ifcconvert/usage.html) documents GLB output, metre default output, `--convert-back-units`, and `--use-world-coords` to bake placement into vertices. Its `--use-element-guids` naming option is listed for OBJ, DAE, STEP and SVG, so the source does not establish that CLI option for GLB. The separate Python [GLB serializer example](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html) shows optional element GUID settings and an explicit metre unit declaration. It establishes an optional SVG route, while the OCS fabrication/export APIs and any PDF or DXF scripting routes require their own evidence.
