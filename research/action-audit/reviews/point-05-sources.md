## Findings

1. **Camera calibration and pose (REC-01, REC-02, CAD-02B, REC-12):** The existing [OpenCV calibration tutorial](https://docs.opencv.org/4.x/dc/dbb/tutorial_py_calibration.html) in the source register documents target object coordinates paired with image detections to estimate camera intrinsics and distortion. The newly inspected [OpenCV 4.13.0 PnP reference](https://docs.opencv.org/4.13.0/d5/d1f/calib3d_solvePnP.html) says `solvePnP` consumes 3D object points, corresponding 2D image projections, camera intrinsics and distortion coefficients. Its `rvec`/`tvec` map object-frame points into camera-frame coordinates (object/world → camera); camera axes are X right, Y down, Z forward. Translation units follow the 3D object-point coordinate units. For iterative PnP, planar initialization needs at least four points via homography decomposition; nonplanar initialization needs at least six points via DLT. IPPE requires at least four coplanar points; IPPE_SQUARE requires exactly four ordered square corners. `solvePnPGeneric` can return alternatives for P3P, AP3P, IPPE, IPPE_SQUARE and SQPNP. P3P uses four points for a unique `solvePnP` result; `solveP3P` with three correspondences may return up to four solutions. The method and point layout therefore affect ambiguity and degeneracy. Image crops, resizes and undistortion must retain their pixel mapping and be reflected in the intrinsics used for each image. Use withheld 3D/2D features and per-point reprojection residuals to check a fitted pose; a low training residual is not a pose-uncertainty estimate or independent evidence of feature identity.
2. **Coarse scan registration (REC-07, REC-12):** [Open3D 0.20.0 global registration](https://www.open3d.org/docs/latest/tutorial/pipelines/global_registration.html) documents downsampling, normal estimation, FPFH feature descriptors and RANSAC feature matching for coarse source/target alignment. Its RANSAC uses `ransac_n` source points and corresponding target points from FPFH neighborhoods; correspondence checkers can screen distance, edge-length similarity and normals. The returned transformation is applied to the source to align it with the target. The tutorial reports a coarse transform on downsampled clouds and then refines it with ICP. Distances, voxel sizes and thresholds use the point-coordinate units; a rigid registration does not determine unknown scale. Symmetry, repeated surfaces, limited overlap, density differences and wrong correspondences can yield plausible alternatives.
3. **ICP and fit metrics (REC-08, REC-12, REC-16, DOM-23):** [Open3D 0.20.0 ICP documentation](https://www.open3d.org/docs/latest/tutorial/pipelines/icp_registration.html) takes source, target, a correspondence distance threshold and an initial transform. `registration_icp` iteratively updates the transform to minimize a selected point-to-point or point-to-plane objective; point-to-plane requires target normals. The output transformation maps source to target coordinates. `evaluate_registration(source, target, threshold, trans_init)` reports `fitness` as inlier correspondences divided by source points and `inlier_rmse` as the RMSE of inlier distances. The source-point denominator is the definition stated by the inspected 0.20.0 tutorial; this record does not assert behavior for other releases or an uninspected local implementation. Fitness is a unitless overlap ratio; RMSE has point-coordinate length units. These metrics describe thresholded fit correspondences, not measurement uncertainty, uniqueness, engineering accuracy or source correctness. Report per-region residual distributions and independent withheld control errors with them.
4. **Point-cloud segmentation and candidate fits (REC-09, CAD-11, REC-14):** [Open3D 0.20.0 point-cloud documentation](https://www.open3d.org/docs/latest/tutorial/geometry/pointcloud.html) documents `segment_plane(distance_threshold, ransac_n, num_iterations)` returning a plane model and inlier point indices. The threshold is a length in cloud units. `cluster_dbscan(eps, min_points)` returns cluster labels; `-1` marks noise. These APIs provide sampled point support and labels. They do not identify a physical plane/cylinder/axis, surface function, design intent or uncertainty of fitted parameters. In particular, a low residual over a short arc can leave a cylinder radius poorly determined; preserve coverage, span, density, noise and withheld residuals, and use a separately evidenced fitter for any cylinder claim.
5. **CloudCompare comparison (REC-16, DOM-23):** The [CloudCompare CLI page](https://cloudcompare.org/doc/wiki/index.php?title=Command_line_mode) documents CLI mode since version 2.3 and shows options for version 2.14.beta. `-C2C_DIST` measures the first loaded/generated cloud (compared) relative to the second (reference); `-C2M_DIST` measures the first cloud relative to the first mesh. Results are scalar distance fields on compared cloud points; `-SPLIT_XYZ` adds component displacement fields for cloud-to-cloud distance, and `-MAX_DIST` bounds nearest-neighbor search. Distances inherit the coordinates' units and frame. These are directed comparisons over sampled geometry, not a symmetric whole-surface error, measurement uncertainty or source-truth test. Preserve compared/reference order, transformations, sampling and distance options.
6. **Blender screen-ray query (REC-13, DOM-19):** The Blender API documentation URL already recorded for `Scene.ray_cast` in the source register was search-indexed and direct retrieval had returned HTTP 402 in the earlier source check. This inspection used official Blender RNA source files: [`rna_scene_api.cc`](https://raw.githubusercontent.com/blender/blender/main/source/blender/makesrna/intern/rna_scene_api.cc) documents `Scene.ray_cast(depsgraph, origin, direction, distance)` against evaluated geometry in world space, with world-space hit location and face normal, face index, original object and matrix outputs. Location, normal and index refer to the evaluated object's mesh in the scene query; the index can be `-1` where original data is unavailable. [`rna_object_api.cc`](https://raw.githubusercontent.com/blender/blender/main/source/blender/makesrna/intern/rna_object_api.cc) documents `Object.ray_cast(origin, direction, distance, depsgraph=...)` in object space against evaluated geometry, returning hit boolean, location, normal and face index. The source URLs are Blender's mutable `main` branch and do not pin an installed release. Screen-to-camera and camera-to-scene transformations remain upstream inputs. A hit confirms intersection with the queried evaluated geometry, not a measured physical surface or a design dimension; near-tangent incidence, occlusion, multiple candidate surfaces and evaluated mesh revision affect interpretation.
7. **IFC local placement, project units and georeferencing (DOM-19, DOM-23):** [IfcOpenShell 0.9.0post1 placement API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/geometry/edit_object_placement/index.html) documents `edit_object_placement(file, product, matrix=None, is_si=True, should_transform_children=False)`. The 4×4 matrix encodes local 3D placement; only local placements are supported. `is_si=True` means matrix translations are SI units; `False` means project units. The child flag controls whether nested elements move with the parent or retain world locations through rewritten local placements. Separately, [IfcOpenShell unit API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/unit/assign_unit/index.html) documents `assign_unit(file, units=None, length=None, area=None, volume=None)` for default project units. The docs list millimetres as the default length unit, square metres for area and cubic metres for volume when no explicit units are supplied. Placement translation convention and project unit assignment are separate inputs and must be recorded separately.
8. **IFC map frame (DOM-19, DOM-23):** [IfcOpenShell 0.9.0post1 georeference API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/georeference/index.html) documents `add_georeferencing` creating projected-CRS and map-conversion entities with parameters blank, then `edit_georeferencing` assigning `IfcProjectedCRS` and coordinate-operation attributes. A CRS name and conversion values must be supplied from the surveyed/project coordinate definition. API creation of the metadata does not estimate a transform, select a CRS, resolve axis order or provide survey control. Keep local model coordinates, placement chain, IFC project units, map conversion and external CRS as distinct frames with explicit transformation direction and independent control checks.

9. **Scan and drawing reconciliation (REC-15, DOM-23):** The inspected registration and directed-distance APIs can align sampled scan/CAD geometry and report residual or per-point distance outputs. They do not resolve whether a scan/drawing discrepancy comes from a revision change, manufacturing allowance, measurement uncertainty or a wrong feature match. Keep drawing nominal, scan estimate, tolerance/allowance and measurement uncertainty as separate claims; use matched feature IDs and reserved controls, and report disagreements without averaging them.

## Evidence limits for the proposed workflow

Camera PnP and point-cloud registration both return transforms, but their coordinate sources differ: PnP maps identified object-frame points to camera coordinates, while Open3D registration maps source-cloud points to target-cloud coordinates. CloudCompare distance fields are computed from an ordered compared object to its reference. Blender `Scene.ray_cast` takes world coordinates; `Object.ray_cast` takes object coordinates. A complete workflow must name each transform's source and destination frames, units, direction, calibration/crop lineage and evaluated geometry revision before chaining operations.

Fitting and pose residuals need held-out controls, documented coverage and alternative solutions. Report camera reprojection, point-cloud inlier metrics, cloud/mesh distance fields, and physical measurement uncertainty as separate quantities. A screen-ray hit or best-fit score is a query result on the selected geometry; it does not establish physical design intent. Georeferencing adds a separately sourced CRS and map conversion to a local IFC placement hierarchy; it does not inherit a CRS from a scan registration.

## Cylinder-fitting source follow-up

Three additional official PCL pages were inspected for the CAD-11 / REC-09 cylinder-fitting dependency. The [PCL cylinder segmentation tutorial](https://pointclouds.org/documentation/tutorials/cylinder_segmentation.html) demonstrates `pcl::SACSegmentationFromNormals<PointXYZ, Normal>` with a point cloud and corresponding normals, model `SACMODEL_CYLINDER`, RANSAC, normal-distance weight `0.1`, maximum iterations `10000`, distance threshold `0.05`, and radius limits `0` to `0.1`. Its example identifies those length values as metres (5 cm threshold and 10 cm maximum radius). `segment(inliers, coefficients)` produces point inlier indices and model coefficients. This is a documented example, not an execution result for project data.

The [SACSegmentationFromNormals API](https://pointclouds.org/documentation/classpcl_1_1_s_a_c_segmentation_from_normals.html) specifies a point cloud plus a corresponding normal cloud as inputs; its segmentation method fills `PointIndices` and `ModelCoefficients`. It documents normal-distance weighting and inherited RANSAC controls, including iteration count, probability, distance threshold, radius limits, axis and angle constraints. The [PCL SampleConsensusModelCylinder header](https://raw.githubusercontent.com/PointCloudLibrary/pcl/master/sample_consensus/include/pcl/sample_consensus/sac_model_cylinder.h) explicitly defines the seven coefficient values in order: indices 0–2 are a point on the axis `(x,y,z)`, 3–5 are axis direction `(x,y,z)`, and 6 is radius. Axis point and radius use input-cloud length units; axis direction is a direction vector. PCL does not attach a physical unit system to these values, so the adapter must preserve the cloud frame and unit and apply distance/radius thresholds in that same unit. The tutorial’s metric example illustrates this convention; a different cloud scale requires correspondingly converted thresholds.

These sources provide an evidenced candidate fitter and adapter contract. The cylinder model still depends on valid corresponding normals, an adequately sampled and visible cylindrical surface, configured thresholds/radius range, and the selected consensus method. The fitted cylinder and inliers describe the supplied sampled cloud; they do not establish physical feature identity, design intent, or parameter uncertainty. A short arc can leave radius weakly constrained, so retain coverage and held-out residual checks.
