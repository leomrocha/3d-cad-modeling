## Findings

1. **Robot tree and URDF units/frames (DOM-08, DOM-09, DOM-31, DOM-37):** ROS REP-103 standardizes ROS quantities on SI units (metres, kilograms, seconds; radians) and right-handed frames, with body axes x forward, y left, z up. The official `urdfdom_headers` rolling `Joint` model stores parent and child link names, a parent-link-to-joint-frame transform, and a joint axis. The child-link frame equals the joint frame. The axis represents rotation for revolute, translation for prismatic, and plane normal for planar joints; fixed and floating joints do not use it. `Link::Inertial` stores an origin pose, mass, and six symmetric inertia entries. These data structures express a parent-child tree; they do not infer a CAD relation's intended joint. REP-103 and the rolling branch may change; preserve the exact source revision/version in any selected adapter.

2. **MuJoCo parse, compile and MJCF serialization (DOM-10, DOM-11, DOM-32, DOM-33, DOM-34):** Current MuJoCo stable documentation describes `MjSpec.from_file()` / `from_string()` parsing MJCF, URDF, MJZ or USD via format decoders; `mj_compile` compiles the editable `mjSpec` to `mjModel`. `MjModel.from_xml_path()` combines parse and compile, so it does not itself provide the editable MJCF output requested by DOM-10. `mj_saveXML`, `mj_saveXMLString` or `mj_encode(..., ".xml", ...)` serialize an `mjSpec`; XML encoding flattens it to one MJCF file. Supplying a compiled model to `mj_encode` copies changed model values back into the spec first.

   Saving follows the spec's `compiler/savecompiled` setting. The documented default `true` saves compilation-made values in canonical form; `false` saves the parsed/authored spec values, without requiring compilation. Saving as written still loses original textual constructs that parsing expands or omits: comments beyond the first file comment, `include` elements, and macro-like `replicate`, `flexcomp`, `attach` and actuator shortcuts. Attached models with different compiler settings cannot always be represented in one saved compiler block. Therefore serialization produces editable MJCF, not a text-preserving rewrite of the original URDF/MJCF. Keep the source file and a mapping/loss report.

   MuJoCo does not impose a physical unit system. MJCF `compiler/angle` defaults to degrees; URDF is interpreted in radians. The MJCF body hierarchy is a tree. MJCF has equality constraints such as `connect` and `weld` for relational constraints; weld removes relative degrees of freedom softly. A closure adapter must preserve the explicit extra edge and identify the specific constraint semantics. URDF import defaults include `compiler/discardvisual=true` and `compiler/fusestatic=true`; fixed/static body fusion can change body counts, while the documentation says its optimization preserves kinematics and dynamics. `discardvisual` can remove purely visual geoms. Record the actual compiler settings and asset results rather than using compiled element counts as source identities.

3. **MJCF inertia and mesh roles (DOM-11, DOM-12, DOM-14, DOM-32):** A MuJoCo inertial frame is located at the body's centre of mass and aligned to principal inertia axes. `diaginertia` is relative to that inertial frame. `fullinertia` takes six values ordered `M11, M22, M33, M12, M13, M23`; the compiler diagonalizes the matrix and sets frame orientation/diagonal values, and rejects non-positive eigenvalues unless `boundinertia` supplies a positive lower bound. With `inertiafromgeom="auto"`, geometry supplies mass/inertia only when a body's inertial element is absent; `true` overrides explicit inertial values. Presence of the inertial element, including its required `pos`, disables automatic inference.

   MuJoCo accepts mesh asset files `.stl`, `.obj` and `.msh`. Its compiler recentres each mesh at the geometric centre and aligns its principal inertia axes to the asset axes. `mjModel.mesh_pos` and `mjModel.mesh_quat` store the translation and rotation offsets made to source-asset vertices; the documentation says those offsets must be reapplied when source vertices are read, then composed with the referencing geom pose. Mesh processing also stores scale in `mjModel.mesh_scale`. A world-space check must apply the compiler asset transform and the geom/body/world transforms; comparing only raw source vertices or `geom_pos` omits documented transforms. The compiler's mesh inertia modes distinguish convex-hull volume, exact watertight oriented-mesh volume, legacy non-convex volume overcounting and shell surface mass. This separates visual mesh, collision decomposition and inertial calculation. CoACD's own README specifically recommends separate convex output parts for engines including MuJoCo when the engine convexifies a whole mesh asset; it does not select the mass distribution or material density.

4. **Convex decomposition CLI (DOM-13, DOM-32, DOM-33, DOM-34):** The current CoACD repository README gives `-i/--input` for OBJ input and `-o/--output` for OBJ or WRL output, with convex components written to that output. `-sp/--split` additionally writes each part under `<output>_parts`; `-t/--threshold` defaults to 0.05 on the README's normalized concavity scale. `-rm/--real-metric` makes the threshold a metre-valued error and requires a metre-scale input mesh. `-c/--max-convex-hull` works only with merge enabled and may create a result above the threshold. The README describes the CLI and limits but no invocation was run here. The project source registry already records CoACD's MIT license and 2022 copyright attribution; imported mesh licences remain per asset.

5. **IFC shape processing and representation boundaries (DOM-15, DOM-16, DOM-27, DOM-34, DOM-35):** IfcOpenShell 0.9.0post1 `geom.create_shape(settings, element, ...)` returns the element ID/GUID, geometry and an element transformation matrix. The mesh-like result carries flattened local vertices, triangle faces, material IDs and item IDs; its rigid transform carries element location and orientation. Element-level processing applies opening subtractions by default. The API can return an OpenCASCADE B-rep when `use-python-opencascade` is enabled; individual shape processing can also select a representation, item or profile. The geometry iterator is recommended for bulk processing, supports multi-core processing and caching, and returns whole elements, not individual representation items/profiles. Its ordinary mesh result uses vertices and triangulated faces; non-triangulated OpenCASCADE B-rep output is a settings-dependent path. The docs do not attach a unit tag to Python mesh vertices. Record the IFC project scale and settings with every geometry result; do not infer metres from the API name.

   The IfcOpenShell GLB serializer example sets `dimensionality`, applies default materials, optionally uses element GUIDs, and declares output units with `setUnitNameAndMagnitude("METER", 1.0)`. IfcConvert usage documentation lists `.glb` as binary glTF 2.0, defaults geometrical output to metres, and supports `--convert-back-units` to retain IFC model units. `--use-world-coords` bakes element placements into mesh coordinates and leaves the matrix identity; otherwise local meshes retain a transform. The CLI supports filtering by GlobalId, but `--use-element-guids` naming is documented only for OBJ, DAE, STEP and SVG, not GLB. Therefore GLB conversion support does not by itself establish durable IFC-to-GLB identity mapping; use a checked sidecar or a serializer path with an explicit ID setting.

   `ifcopenshell.api.geometry.add_representation(...)` accepts an IFC geometric context plus a Blender object/data geometry, optional coordinate offset in SI units and unit scale; it returns an `IfcShapeRepresentation` or `None`. It does not by itself create an IFC product, class, placement or spatial relationship. Use the separately sourced product/relationship authoring operations for DOM-15 and DOM-35. This API is Blender-dependent and does not establish generic import of all library source formats.

7. **Mass, centre of mass and inertia method (DOM-14; supports DOM-11/DOM-32):** Open CASCADE 8.0.1 `BRepGProp::VolumeProperties(shape, props, ...)` computes volume global properties for a finite solid or coherently oriented finite solids and accumulates them into `GProp_GProps`; it attaches no volume density, so unit-density `Mass()` equals volume. The source requires the input to have no free boundary and warns that orientation/coherence conditions are not checked; `UseTriangulation` selects triangulated data, while false uses exact surfaces. Its overload with `Eps` performs adaptive 2D Gauss integration, reports an estimated relative error, and switches to non-adaptive integration when `Eps > 0.001`. `GProp_GProps` is the result/accumulator: `Mass()`, `CentreOfMass()` and `MatrixOfInertia()` expose mass, absolute-frame COM, and central symmetric inertia tensor with axes parallel to absolute Cartesian axes. Its `Add(component, density)` composes already-computed properties and applies Huygens' theorem (parallel-axis shift) when reference points differ. The integral result therefore needs an explicitly unit-consistent density step to obtain physical mass and inertia; the geometric integrals alone do not provide material density. The API does not embed a unit system, so coordinate length units determine volume units cubed and central inertia units are mass times length squared after density is applied. The reference advises a nearby accumulation point for numerical accuracy and warns against applying density twice.

   **Proposed checked calculation algorithm:** For each valid solid with documented density, obtain volume integrals with `BRepGProp::VolumeProperties`, then apply density once in coherent units to obtain mass, centre and central tensor; rotate its tensor into the named assembly axes with `I_target = R I_centre Rᵀ`; translate the tensor to a chosen assembly origin with `I_o = I_centre + m((r·r) identity - rrᵀ)`; sum component mass and origin tensors; then shift the aggregate tensor to the weighted aggregate centre. `GProp_GProps.Add` can perform component accumulation and parallel-axis shifts when all component frames/reference points are correctly represented. Check symmetry, positive principal moments and principal-moment triangle inequalities, and independently compare the mass and centre against measurements. A geometry-based result requires a closed, coherently oriented finite solid and density per material; the source API does not itself validate these conditions. The algorithm does not turn a visual material label or a scalar scale weight into measured inertia.
